# Scaffold with kay new and kay add

`kay new` scaffolds a project from presets and features, and `kay add` adds a feature to one that exists. The rest of the commands are in [Project setup and scaffolding](project.md).

## Common tasks

### Scaffold a project

`kay new` takes a directory, a preset and the features to add or drop:

```sh
kay new my-site --template site --with search
```

### Add a feature to a project

`kay add` writes what a feature needs into a project that exists, and `kay add auth,ui` adds the libraries' features:

```sh
kay add postgres
```

### Generate a page, a component or an API module

`kay generate` writes a starter file of the kind in its folder, and a test of it when the project has tests:

```sh
kay generate page pricing
kay generate action team/removeTissue
kay generate resource post title:string body:text published:boolean
```

## Reference

- `kay new <dir> [--kay <dependency>] [--template blank|server|site|app] [--with <features>] [--without <features>] [--forge forgejo|github] [--runner <label>] [-y] [--dry-run] [--format text|json] [--quiet]`:
  - Scaffold a project in an empty directory.
  - A project is a set of features: `server` (an Elysia server; off, a static site), `starter` (a header, a skip link, a `_404.kay`, a home page greeting from the server with a counter island), `tailwind` (Tailwind through `bun-plugin-tailwind` over the Catppuccin Mocha palette, with the `.vscode/settings.json` every project gets also pointing Tailwind IntelliSense at the shorthand and `class="..."`; off, the markup carries no classes), `accents` (an accent picker in the header, kept in a cookie, which needs `starter` and `tailwind`), `eslint`, `tests`, `ci` (the workflow below, Forgejo's or GitHub's), `docker` (the container below; a static site's brings a `_404.kay` when `starter` is off, for its nginx 404), `auth` (kayjs-auth: what `kay add auth` writes, its users in a SQLite file, which needs `server` and `tailwind`), `postgres` (kayjs-auth's users in Postgres instead, with its compose stack and roles, which needs `auth`) and `ws` (the app's API module and websocket island, shown on the home page, which needs `server`).
  - A preset names a set: `blank` none, one layout and one bare page built as a static site; `server`, `site` and `app` as described below.
  - Run in a terminal with none of `--template`, `--with`, `--without` or `-y`, it asks for a preset, then shows its features as a checklist. Checking a feature checks what it needs, and unchecking one unchecks what needs it.
  - Otherwise it takes `--template`, `server` by default, adds the comma-separated `--with` features and drops the `--without` ones, and refuses a feature listed in both, or one missing what it needs (`kay: accents needs tailwind: add --with tailwind, or drop it with --without accents`);
  - `--forge forgejo|github` names where the repository lives (`--host` still works until 1.73, with a warning that `--quiet` leaves out, as `kay dev --host` is an address), which decides the `ci` workflow: `.forgejo/workflows/*.yml` on a `debian` runner, or `.github/workflows/*.yml` on `ubuntu-latest` with `oven-sh/setup-bun` and, for an app with `postgres`, its Postgres service on `localhost:5432`; both run `kay check --format github`, so each problem shows on the diff, with `contents: read` permission alone (the Pages workflows add what publishing needs) and every action pinned to the commit of a release, its version in a comment. Without it the host is read from the `origin` remote of `dir`, or of the directory above it that exists, `github` for github.com and `forgejo` for any other remote or none. `--runner <label>` names another runner label for either.
  - Every project has the `.npmrc` naming the registry kay comes from.
  - The `server`, `site` and `app` presets have a layout with `seo` defaults and a skip link, a header with an accent picker over the Catppuccin Mocha palette, kept in a cookie, Tailwind through `bun-plugin-tailwind`, and Tabler icons.
  - `server`, the default, is an Elysia server, with a `Dockerfile` and `compose.prod.yaml` running the executable `bun run compile` makes.
  - `site` is a static site whose `bun run build` runs `kay build --static`, its pages showing the default accent until the picker hydrates, since no server reads the cookie, with a Forgejo Pages workflow publishing `dist` to the `gitea-pages` branch under `/<owner>/<repo>`, its `SITE_URL` a placeholder to replace with the host the Forgejo instance publishes Pages on (`--forge github`: a workflow deploying `dist` with GitHub Pages, `SITE_URL` and `SITE_BASE` read from the repository), and a `Dockerfile` serving it with `nginxinc/nginx-unprivileged` on port 8080 instead.
  - `app` is the server with kayjs-auth as `kay add auth` writes it (`auth({ name })` and `ui()` in `kay.config.ts`, a root `src/routes/_guard.ts` exporting kayjs-auth's `guard()` to put every page behind sign-in, and no `src/auth.ts`), an API module and an island over its websocket, its session secret written to a `.env` git ignores, `.env.test` holding a test-only secret, and `.env.example` naming what production sets (`SESSION_SECRET`, `SITE_URL`);
  - The default `app` needs Bun alone: kayjs-auth keeps its users in `data/auth.db` and creates its tables when the app starts, `data` is ignored by git and docker, and `compose.prod.yaml` mounts a `data` volume the image prepares for `nobody`, the user it runs as, with no database service and no migration;
  - `--with postgres` (with `auth`, as in `--template app --with postgres`) swaps SQLite for Postgres: `src/db/tables.ts` lists `...authTables` among the tables, which `src/db/index.ts` builds `db` over and `pg-orm.config.ts` imports on their own, so the test preload points `DATABASE_URL` at its copy before anything builds `db`, `docker compose up -d --wait` starts the database `compose.dev.yaml` describes, `bun run db:generate init` writes the first migration for kayjs-auth's tables as the installed version declares them (and the next ones for yours), `bun run db:migrate` applies `migrations/`, its `bun run test` gives each test file a copy of the migrated database (see [Testing](testing.md)), its workflow runs Postgres as a service, and `compose.prod.yaml` runs the database and a one-shot service applying the migrations before the app. Two Postgres roles split the work: the owner (`POSTGRES_USER`, connected by `MIGRATE_DATABASE_URL`, which `pg-orm.config.ts` reads before `DATABASE_URL`) changes the schema, and `app_rw` (the app's `DATABASE_URL`, password `APP_DB_PASSWORD`) reads and writes rows and cannot drop, alter or create anything. The database image creates `app_rw` from `db/roles.sh` when it first creates the database, with default privileges on tables, sequences and schemas, so a table a later migration creates needs no `GRANT`. An existing database runs `db/roles.sh` once, see [Upgrading](upgrading.md);
  - Every server preset's compose publishes the app on 127.0.0.1 alone, for a reverse proxy serving it over HTTPS, and its `kay.config.ts` sets `proxy: true` so rate limits count the visitor and not the proxy, its images and workflow use the Bun `kay new` ran under, and `.env` is ignored by git and docker and written readable by its owner alone;
  - `--kay` sets the `kay` dependency, by default `npm:@kaynooo/kayjs@~<its version>`, or a packed copy when run from a checkout of kay.
  - The package is named after the directory, lower case with other characters turned into `-`.
  - Every template's `tsconfig.json` adds `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride` and `noFallthroughCasesInSwitch` to `strict`, as kay does itself, so an optional field passed `undefined` must say `?: T | undefined`;
  - `server` and `app` carry a workflow checking, linting and testing the project on every push, and the `site` workflow tests it before building, which checks it, then lints it (see [Linting](checks.md#linting)).
  - Every project also has an `AGENTS.md` pointing coding agents at kay's docs for the installed version, through a `@node_modules/kay/llms.txt` line Claude Code expands at the start of a session, saying that every page title ends with `seo.name`, which `kay new` filled in from the folder name (left out by `kay migrate astro`, whose pages keep their own titles), and naming the checks its scripts run; a project without one adds it by hand.
- `kay generate <page|component|island|action|api|guard|resource> <name> [field:type...] [dir] [--dry-run] [--format text|json] [--quiet]`:
  - Writes a starter file into the project in `dir` (the current directory by default), by `<name>`, and never over a file that exists: one that does stops it with `kay generate: nothing was written`.
  - `page pricing` writes `src/routes/pricing.kay` (`blog/[slug]` and `(group)/about` are routes too; its `h1` takes Tailwind's shorthand classes when the project has Tailwind), `component card` and `island likes` write `src/components/card.kay` (a `label` prop) and `src/components/likes.kay` (a signal and a button), `api notes` writes `src/api/notes.ts` (`api().get('/')`), `guard admin` writes `src/routes/admin/_guard.ts` (`/` for the root one; its function does nothing, for you to write the rule in) and `action team/removeTissue` writes the action `removeTissue` into `src/routes/team/_actions.kay` (a schema and a handler). An `_actions.kay` that holds a server fence alone gets the action appended (`import { s } from 'kay'` added when it lacks it); one already exporting that name stops the command, and one with a template or other fences is left alone and the command prints the action to add by hand.
  - A project with `tests` (`bunfig.toml`) also gets `tests/<name>.test.ts` for a page (it visits the URL, a project with `auth` expecting the redirect to sign in), `tests/action-<name>.test.ts` for an action (`site.call` and `site.refusal`) and `tests/api-<name>.test.ts` for an API module (`site.api`) and `tests/guard-<name>.test.ts` for a guard with a page below its folder (it visits the shallowest one, a project with `auth` expecting the redirect to sign in), a `/` in the name written `-`; none for a component or an island, nor for a guard with no page below, nor for a page with a param, and none for an action or API module in a project with `auth`, whose guard answers first.
  - `resource post title:string body:text` (a project with `postgres`, else it stops naming `kay add postgres`; the fields are `name:type`, the type `string` (varchar 200), `text`, `int`, `float` or `boolean`, all required, and `name`, written `blog-post` or `blogPost`, gives the table `blog_post`, `BlogPost` and the folder `src/routes/blog-posts`) writes the pg-orm table `src/db/<name>.ts`, added to `tables` in `src/db/tables.ts`, an `_actions.kay` with `create`, `update` and `remove` over `s` schemas built from the fields (each redirecting to the list), the list at `/blog-posts` and the edit page `[id=integer]/edit.kay` with a delete button. With kayjs-ui installed the list is a `Table` in `src/components/blog-posts-table.kay`, the create form a `FormDialog` in `src/components/new-blog-post.kay` and the edit page a `SaveForm`; else the list is a plain `table`, with a `new.kay` page of `form`s. A project with tests gets `tests/blog-posts.test.ts`, which creates a row and reads the list, edits and deletes it, and refuses a create with an empty text field (a word for a number when there is none). A `tables` list holding a comment or an index is left alone and the command stops, naming what to add. Run `bun run db:generate` and `bun run db:migrate` for the new table.
  - What it writes passes `kay check` and the lint. `--dry-run` lists the files and writes none, and `--format json` prints `{ kind, name, written, dryRun }`.
- `kay add <features> [dir] [--no-install] [--dry-run] [--format text|json] [--quiet]`:
  - Applies `kay new` features, comma-separated, to the project in `dir` (the current directory by default): the files and edits `kay new --with` would have made, then `bun install`.
  - The features the project holds are read off its files. A feature missing what it needs is refused naming the command that adds them together (`kay add server,ws`); `kay add postgres` on a project without kayjs-auth plans it too, `kay add auth,postgres` writes both in one run, and `postgres` over an app whose `data/auth.db` exists stops there, as that file holds the users.
  - It writes only when every file has the shape `kay new` writes: a file both feature sets write differently (`_layout.kay`, `bunfig.toml`, `kay.config.ts`) is replaced while it is still what `kay new` wrote, `package.json` gets the scripts and dependencies it lacks (a script is replaced only while it is still the generated one), `.gitignore`, `.dockerignore` and `.env` get the lines or keys they lack, and `AGENTS.md` is left once edited; a deleted file is not written back and is named in the output. The CI workflow follows the `origin` remote (`.github` for GitHub, `.forgejo` otherwise), else the folder the project has, and the runner label is the one its workflow already runs on. Any other file, or a file that exists with other content, stops it with `kay add: nothing was written` and the lines to remove (`-`) and add (`+`) by hand.
  - `ai`, `mail`, `cms`, `ui` and `auth` are features of kay's libraries (`auth` is kayjs-auth, which `kay new --with auth` writes the same files for): it adds `@kaynooo/kayjs-ai`, `@kaynooo/kayjs-mail`, `@kaynooo/kayjs-cms`, `@kaynooo/kayjs-ui` or `@kaynooo/kayjs-auth` (the last two with `@iconify-json/tabler`, kayjs-auth with `@kaynooo/pg-orm` and kayjs-ui) at kay's own minor, then writes what the package's `add` export says (`{ description, files?, edits?, env?, example?, ignore?, extension?: { import, expression }, notes? }`, or a function of the project returning it) and adds the extension to `extensions` in `kay.config.ts`, which needs a plain `defineConfig({ ... })`. `ui` needs `tailwind` and `auth` needs `server` and `tailwind`, refused like a core feature; `kay add ui` writes only `ui()` (see [Extensions](component-libraries.md#extensions)), and `kay add auth` writes `src/auth.ts` over the app's pg-orm `Database` (`...authTables` added to its `tables`, and `authMailer(mail.enqueue)` as the mailer when `src/mail.ts` exports `mail` and `kay.config.ts` registers `mail({ module })`, else the bare `{ send: mail.enqueue }`; `.gitignore` is created when absent and `data` is added unless `/data` or `data/` is there) or a SQLite file of its own, `src/routes/_guard.ts` guarding every page, `authPages(...)`, `ui()`, and `KAY_SECRET` and `SITE_URL` in `.env.example`. The import goes where the app's `perfectionist/sort-imports` puts it (groups, then natural order), so a config with sorted imports passes `kay lint` with no fixer run.
