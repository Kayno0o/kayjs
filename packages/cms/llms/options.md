# Options of cms()

The options `cms()` takes, from `kay.config.ts`.

`cms({ prefix, logo, guard, roles, member, files, uploads, pageSize, collections, rawHtml, author, onSave, history })`: `prefix` is where the screens live (`/admin`; `/` is the root, where the screens mount under a `(admin)` group, so an app root layout and guard neither wrap them nor are wrapped by theirs), `logo` an image (`/logo.svg` or an https URL) before the name in the admin's header, `pageSize` how many entries a collection's list shows on a page (50), a positive whole number, `collections` how the screens arrange a collection by name, `{ form: { fields, hide }, list: { columns, actions } }` (see [Arranging and replacing the screens](screens.md)), `guard` who may use them and the API, as `{ load }` returning the guard, which runs on the first request so `kay.config.ts` imports nothing of the app's auth or database, or the built guard itself, which does import it, `files` where a folder entry's file goes, `workingTree()` by default, which a production server refuses to boot with unless named, as the next deploy would drop its saves. `uploads` lists the types a file field takes, exact or `image/*`, PNG, JPEG, WebP, GIF, AVIF and PDF by default, the type read off the file name's extension, in any case, as kay's storage serves it; another is answered 415. The bytes must be that type too, whatever the name or the declared type says: PNG, JPEG, GIF, WebP and AVIF are read by their signatures, a PDF by its header, an SVG by its `<svg` root, and a file that is not what it is named (HTML named `x.png`, a JPEG named `x.png`, a PNG cut short of its header) is answered 415 with `cms.upload.notReal`; a type with no signature (`text/csv`, video) is taken as named, and storage serves anything but a PNG, JPEG, WebP, GIF, AVIF, video, audio, PDF or plain-text type as a sandboxed download, an SVG included, so it never runs as the site; the SVG check is only for a `<svg` root in the first 4 KB. `uploads: { types, maxSize }` also sets the most an upload may weigh, bytes or `'50mb'` as kay's `budget` takes them, 20 MB by default; the upload route reads that much whatever the app's `bodyLimit`, so nothing else is raised, and a `maxSize` that is zero, negative, fractional in bytes or over 128 MB less 64 KB throws as `kay.config.ts` loads, as Bun refuses a request body over 128 MB before the route sees it and buffers an upload in memory. A save whose body renders HTML that would run as the site or cover it, every tag and attribute kay's sanitizer drops (a `<script>`, an `<svg>`, a `<form>` or an input, an `on*`, `style` or `formaction` attribute), a `javascript:` URL in any URL attribute, or a tag left open or wrapped around a component, read off the HTML kay renders as a browser tokenizes it, is refused with an issue on the body, unless `rawHtml` lists its collection; the collection's own components, HTML in code and Markdown's task lists pass, and publishing keeps the stored body unchecked. `author` names who a save is committed as, and who the entry screen lists as also open in its entry (kay's `presence()`, the names of the other editors, else how many), from the guard's context, so only with a `guard`; without it the forge commits as the account behind its token and no editor's name or email reaches git, and git history cannot be erased (RGPD art. 17), so prefer a pseudonym such as `{ name: \`Editor ${user.id}\`, email: \`${user.id}@users.noreply.example.com\` }` unless the editors agreed to stay in the history for good; a real identity is written like this: `author: async ({ locals }) => { const user = await locals.auth.user(); return user && { name: user.name, email: user.email } }`.

`onSave({ collection, slug, locale, verb, author, commit })` runs after each save, publish, duplicate, move, restore and deletion that went through, a throw being logged and never undoing the save ([After a save](loaders.md#after-a-save)).

`history` is `false` to keep no revisions nor deleted entries, or `{ revisions, trash }`: the saves kept per entry, 50 by default, and how long a deleted entry is kept, `'30d'` by default, `false` for none; `collections: { name: { history: false } }` leaves one collection out ([History, the trash and the activity log](history.md)).

## Signing in and roles

- A visitor the guard refuses with a 401 (kayjs-auth's `auth.guard()` without a sign-in page, `passwordGuard`) is redirected on a read to the sign-in, `?redirect=` set to the exact path and query asked for (through `localPath`, so a value leaving the site leads to `prefix`): kayjs-auth's `signInUrl(back)` when `ctx.locals.auth` has it, else the cms's `<prefix>/sign-in` for a `passwordGuard`. A guard that redirects itself (`auth.guard()` with `pages`) is left alone. A post is answered 401.
- `passwordGuard(password | { role: password }, { maxAge = '14d' })` is a guard for a site with no users: `cms({ guard: passwordGuard(env.EDITOR_PASSWORD) })`, a lone password signing in as `editor`. `<prefix>/sign-in` takes the password (10 tries per 15 minutes) and sets `kcms_session`, `HttpOnly`, `SameSite=Lax`, `Secure` over https, holding `role.expires.signature`, the signature an HMAC with a key made from that role's password, so changing a password ends its sign-ins and a forged role or date fails. An empty password, an unset variable included, throws; a role is letters, digits, `_` and `-`. `passwordGuard(passwords, { secret })` mixes the app's own secret into the signing key (the key is also stretched with scrypt, so a cookie seen once does not give the password away offline), and the same password on another site then signs in nowhere else. Sign-out deletes the cookie and ends it in this process, so a copy stops working too; another process or a restart still takes a copy until it expires or a password changes. The sign-in's rate limit is per client address, so behind a proxy set kay's `proxy` option or every editor shares one bucket. It must be the `guard` itself or the `load` result: a guard wrapped by the app is not recognised and shows no sign-in screen. Use kayjs-auth when there are members.
- A test signs a site in through `passwordGuard` with `@kaynooo/kayjs-cms/test`, no form: `await cmsSignInAs(site, 'admin')` sets the sign-in cookie of that role (left out when the guard holds one password) and returns it, a second call switches role, and `cmsSignOut(site)` makes the site anonymous again, its other cookies kept. `await cmsSignInWith(site, password)` posts the sign-in form as a visitor does, to test a wrong password (401) or the right one. Both throw when the cms is not on a `passwordGuard`.
- The admin header names who is signed in (kayjs-auth's username, else email, else id; the role for `passwordGuard`) and has Sign out, which ends the password cookie or kayjs-auth's session (`auth.signOut()`) and goes to the site's home.
- `roles: { role: ['publish' | 'delete' | 'upload' | 'redirects'] }` names what each role may do beyond editing, and needs a `guard`. Without it everyone admitted may do all. With it a person holding no listed role only edits, and the actions of their roles add up. `publish` covers `/publish` and `/unpublish`, and a save that changes the collection's draft flag or its publish or unpublish date (a new entry must be a draft with neither set; in a collection with a publish date and no draft flag a role without `publish` still creates entries, which the server writes with a far publish date, `9999-12-31`, until a publisher sets one). A custom guard that is neither kayjs-auth nor `passwordGuard` holds no role unless `cms({ member: ({ locals }) => locals.user && { name: locals.user.email, roles: locals.user.roles } })` reports who the guard let in (it also runs where no guard does, so return nothing for a visitor; it replaces kayjs-auth's lookup, the password guard still comes first): `roles` are matched against the names `roles` lists, `name` is shown in the admin header, and a `member` that returns nothing holds no role; `delete` covers an entry and the unused uploads; `upload` the file route; `redirects` the redirects API, the `not-found` screen and an entry's slug rename, which makes a redirect. A role is checked on the server: kayjs-auth's through `auth.isGranted(role, user)`, so its hierarchy counts, the password guard's from the signed cookie; nothing the request states counts. A refusal is a 403 naming the action (`cms.guard.forbidden`). The screens disable what the role may not do, with that sentence as the tooltip: Publish, Unpublish, Publish now and the schedule buttons, Delete (also in the list and its bulk bar and on the unused uploads), the draft flag and the publish and end dates of an entry's form (read-only), the upload zone of file fields and the image drop and paste of a Markdown box, the Rename button and the Missing pages link; the server refuses it all the same.
- An editor whose sign-in ended mid-edit gets `cms.session.toast` and a notice with a link to `/api/cms/sign-in?redirect=<page>` in a new tab, `cms.session.ended`, in place of the failure of the save, delete, publish, unpublish, move or redirect call; the edits stay in the form and the next successful call clears it.
