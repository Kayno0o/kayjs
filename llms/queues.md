# Queues

A `queue` runs jobs in the background, each surviving a restart, and a `workflow` is a multi-step flow that sleeps and waits for events across restarts; `schedule` and `background` are in [Running in production](production.md#background-jobs).

## Common tasks

### Run a job in the background

A queue holds jobs that must not be lost: an action enqueues one and goes on, and the server runs it in the background, after a restart or a deploy if need be:

```ts
// src/jobs.ts
import { queue } from 'kay/server'

export const welcomeMails = queue(
  'welcome-mails',
  async ({ to }: { to: string }) => sendWelcome(to),
  { attempts: 5, backoff: '30s' },
)
```

```ts
// src/plugins/jobs.ts, or `.use(welcomeMails)` before `pages()` in src/server.ts
export { welcomeMails as default } from '../jobs'
```

### Delay a job or keep one per key

`enqueue` takes a `delay`, and a `key` keeps one job waiting or running for it:

```ts
await welcomeMails.enqueue({ to: email }, { delay: '1h', key: email })
```

### Show a queue's jobs on a page

`live` on a queue lets an island list its waiting and running jobs, following them as they are added, taken, done or failed, with no route or `live()` value written:

```ts
// src/jobs.ts: `live: true` would send the whole payload, key, progress and last error
export const scans = queue('scans', scan, { live: ({ target }: { target: string }) => ({ target }) })
```

```kay
---
import { jobs } from 'kay'
---
for job of jobs<{ target: string }>('scans')
  p {job.payload.target}: {job.status}
```

### Write a flow that sleeps and waits

A `workflow` runs steps once each, keeps their results in the job store and survives restarts. `start` and `send` are one call each, and the `id` names the run. Used like a queue: `.use(onboarding)`, or `export { onboarding as default } from '../jobs'` in a plugin file.

```ts
// src/jobs.ts
import { workflow } from 'kay/server'

export const onboarding = workflow<{ userId: string }, { visited: undefined }>('onboarding', async ({ input, step }) => {
  await step.run('welcome', () => sendWelcome(input.userId))

  const visit = await step.waitFor('visited', { timeout: '3d' })

  if (visit.timedOut)
    await step.run('reminder', () => sendReminder(input.userId))
})
```

```ts
await onboarding.start({ userId }, { id: userId })
await onboarding.send(userId, 'visited')
```

## Reference

- `workflow<Input, Events>(name, ({ id, input, step }) => ..., options)` is an Elysia plugin like `queue`, `options` those of a queue (`store`, `attempts`, `backoff`, `concurrency`, `lostAfter`, `idlePoll`, `keepFailed`) and `onFailed({ id, input, error })`. A run is one job of the queue `workflow:<name>`, kept under its id as its `key`, on the same stores as queues, its results in the job's payload after each step: no table of its own.
- `start(input, { id?, delay? })` resolves with the run's id (random unless given): while a run with that `id` is live it starts nothing and resolves with the same id. `send(id, event, data?)` resolves with whether the run was waiting for that event, waking it at once in this process and within `idlePoll` in others; an event sent while the run waits for another, sleeps or has not started is kept in the run for the wait that names it, one sent while a worker holds the run (a step running, or just taken after a timeout) is dropped, and `send` resolves with whether it was taken. `status(id)` resolves with `{ status: 'running' | 'sleeping' | 'waiting' | 'failed', steps, event?, error? }`, undefined once the run completed. `cancel(id)` ends a run, a running one at its next step. `drain()` is a queue's.
- The function runs again from its top each time a process takes the run, and a finished step returns its kept result: what lies between steps must be deterministic. A step is awaited before the next (two at once throw), a renamed or reordered step under a live run fails it naming the step, and a result devalue cannot keep throws.
- `step.run(name, work)` runs `work(signal)` once and keeps its result. `step.sleep('3d')` and `step.waitFor(event, { timeout? })` write the run's state and give its hold back (the job is due at the wake time, never for a wait without timeout), so no process holds it and the code after them runs in whichever process takes the run; the step's promise never settles in the claim that suspended, so a `try` around it catches nothing. `waitFor(event)` resolves with the data, with `timeout` with `{ timedOut: false, data }` or `{ timedOut: true }`. `Events` types `waitFor` and `send`.
- A step that throws, or a run that dies, uses the queue's retries: a stop hands the run back at once, a dead process holds it until `lostAfter`, and a retry replays from the first step with no kept result. A kept step starts the attempts count again, so a long flow does not spend its attempts across steps. A stop or lost hold ends the run before its next step, so no step starts beside the process taking over. A step changed under a live run fails it at once, with no retry, and a run keeps at most 50 events no wait named yet, the oldest dropped and logged, and a flow edited to end earlier than its kept steps completes without an error. `lostAfter` bounds the time between two sleeps or waits. `retryLater` works in a step. The payload holds the input and every kept result, rewritten after each step (shown by the jobs page, kept 30 days when the run fails, with no `redact`), so keep results small and free of secrets. In tests `site.runJobs()` runs the due steps, and `setSystemTime` moves a sleep or a timeout along.
- A `JobStore` needs `update`, `release` and `state` for a workflow, as `memoryJobs`, `sqliteJobs` and `pgJobs` have (no schema change): `update(id, { payload, runAt? }, { until })` writes only while `until` is the job's hold and counts the run as started once, `update(id, change, { payload, now })` writes only while the job is not held and its payload is still that text, which is how an event wakes a run once against a timeout.

- An action calls `await welcomeMails.enqueue({ to: email })`, or `enqueue(payload, { delay: '1h' })` to run it later.
- `queue(name, handler, options)` is an Elysia plugin: the server using it runs the queue's jobs from start to stop, `concurrency` at a time, 1 by default, and waits on stop for the runs in progress.
- A process that only enqueues, a script say, need not use it.
- Jobs wait in a store shared by every process of the machine opening it: `sqliteJobs('data/jobs.sqlite')` by default, its file and directory created by the first job enqueued or schedule locked, which every schedule of a production server does by default, so its `data/` must be writable there; a dev or test server whose queues never get a job writes nothing.
- `sqliteJobs(path)` and `memoryJobs()` from `kay/server` make a `store` of another file or one kept in the process, and `JobStore` is the shape of an app's own.
- `pgJobs(db)` keeps the jobs in Postgres, for replicas on several machines: `db` is a Bun `SQL`, a pg-orm `Database` or a connection URL, and `store: { jobs: pgJobs(db) }` in kay.config.ts gives it to every queue and locked schedule. On pg-orm it needs nothing but the tables in the app's schema: `import { jobTables } from 'kay/pg-orm'` and `new Database({ tables: [...yourTables, ...jobTables] })` (pg-orm is an optional peer of kay, which installs and builds without it), and `db.sync()` or `pg-orm generate` creates `kay_jobs` and `kay_locks` with their indexes, matching what the store expects, for the owner's migration to run, so the app template's `app_rw`, which creates nothing, finds them (`import { pgJobs } from 'kay/server'` then `pgJobs(db)`). Without pg-orm migrations, `pgJobs` looks for them and creates them only when missing, which takes a role that may create tables, else the owner runs `import { createJobTables } from 'kay/server'` then `await createJobTables(db)` (idempotent, safe from replicas at once: an index missing on tables already there is built by one replica at a time, under a Postgres session lock, and the others wait for the unique ones before enqueuing, which needs a direct or session-mode connection, not a transaction-mode pooler) in a boot script; pg-orm then sees those two as unknown tables, so name them in `ignoreTables`: `import { jobTables } from 'kay/server'` there is the list of their names, `ignoreTables: [...jobTables]`. A claim is one `UPDATE` over `FOR UPDATE SKIP LOCKED`, and a hold lasts from the database's clock, whichever replica claims, so replicas' clocks need not agree.
- `pgData(db)` is `sqliteData(path)` on Postgres, for replicas on several machines: `import { pgData } from 'kay/server'` then `store: pgData(db)` in kay.config.ts keeps the sessions, `cached` values, jobs, schedule locks, rate counts, presence members, `live()` values and Web Vitals in `kay_*` tables of the same database, `db` a Bun `SQL`, a pg-orm `Database` or a connection URL as `pgJobs` takes. The tables are created when missing, which takes a role that may create tables; else the owner runs `await createDataTables(db)` (idempotent, safe from replicas at once, the jobs' tables included) in a boot script and names `dataTables` from `kay/server` in pg-orm's `ignoreTables`. Replicas hear each other's `invalidate`, `live()` changes and room messages by polling (about half a second for the cache and live values, up to 5 seconds when idle, 250 ms for rooms), no LISTEN, so a pooler in front of Postgres is fine (a missing index is built on a session connection). One timer per connection serves all three, a read or write that takes over 30 seconds is given up, and live writes waiting behind a database that stopped answering are dropped (logged) past 10,000. Every call of the job, session, rate, cache, notification, vitals and rooms stores is given up after 8 seconds (inside the default `shutdownTimeout`) with a logged error rather than hanging, the sweeps, `deleteWhere`, `prune` and the job listings after 150 seconds as they scan a table, a rooms `state` or `update` within 8 seconds however many writes are queued before it, room writes waiting behind it are dropped past 1,000, and a connection `pgData` or `pgJobs` opens from a URL times out connecting after 10 seconds, closes when idle for 60 and is replaced after 30 minutes. A room's state is kept in `kay_room_state` too, changed one update at a time across replicas, so `rooms({ store: pgData(db).rooms, state })` works with `state` and `update` resolving promises ([Rooms](rooms.md)). One database belongs to one app: the first app to boot on it records its package.json `name` in `kay_meta` (a database from before this has none, and adopts the first app that boots), and another app starting on it fails its boot naming both, since `kay_*` tables carry no app scope and a `mail` queue, a `live()` id or a cache key would be shared; give each app its own database. A renamed app takes its database over by starting once with `KAY_ADOPT_DATABASE=<the old name>` (only that owner is adopted, so leaving it set is harmless); an app with no package.json name claims nothing, two apps sharing a name are one app to it, and a bare `pgJobs(db)` outside `pgData` records no owner. kay chose this over prefixing every key and queue by app name, which would orphan the data of a rename silently. Rate keys are pseudonymised by the app secret, else by a random key in `kay_meta` every replica reads. `pgData(db).sessions` has `deleteWhere` like `sqliteStore`. A store opened outside `kay dev` (a script, a test, a one-off process) is closed with `await store.close()`, or `await using store = pgData(url)`, which ends the polling, timers and room membership of every kind and closes the pool when `db` was a URL; a `SQL` or a pg-orm `Database` handed in stays open, as it is the caller's. A `kay dev` reload closes the store of the module that ran again by itself.
- `jobs: { guard }` in kay.config.ts serves `/_kay/jobs` in production: each queue's waiting, running and failed jobs with payload and error, and forms to retry or delete one. A `workflow()` run shows its state (running, sleeping until a time, waiting for an event, failed) and its kept steps, with a form to send the event it waits for (a field takes its data as JSON) and one to cancel it, in the Jobs tab and on this page alike. `guard` is a guard or a list of them, such as `ctx => ctx.locals.auth.requireAdmin()`, run on every request; without one the boot stops. The page is plain HTML with no script, answers `no-store` and `noindex`, `jobs: { guard, path }` moves it, and `kay dev` serves none (its Jobs tab covers it).
- A `JobStore` may also have `revive(id, runAt)`, which puts a failed job back to wait with its attempts given back and resolves with whether it did (false for a job not failed, or whose key a live job holds since), as `sqliteJobs`, `memoryJobs` and `pgJobs` do: the dev tool's Jobs tab retries a failed job with it ([The dev tool](dev-tool.md#reference)). `jobs(queue, { limit?, failed? })` and `failed(queue, limit?)` list the jobs by when they are due, the earliest first, and may cut their result in the store's query: the Jobs tab and page ask for 101 of each, so a long queue is not read whole, and a store ignoring the options is cut after.
- A `JobStore` may also have `state(queue, ref, now)`, `progress(id, until, progress)` and `release(id, until, runAt?)`, and its `add(job)` may resolve with the id of the live job already holding `job.key`, in which case it stored nothing: `sqliteJobs` and `memoryJobs` do all of these. A file made by an older kay gains the columns on first open. A run's writes about its job are matched against the hold it was claimed with, so one that outlived its hold changes nothing of the job another process holds: `claim` may return the hold it stored in the job's `heldUntil` (`pgJobs` does, from the database's clock; the `until` asked for stands otherwise), and `complete(id, until?)`, `retry(id, runAt, error, until?)` and `fail(id, error, payload?, until?)` write only while `until` is still the job's, `remove()` and the purge naming none. A store ignoring the extra argument keeps working, without the guard. `retry` and `fail` may resolve with `false` for a write the guard refused, and the run then logs nothing and calls neither `onError` nor `onFailed`, the job being the other process's now; resolving with nothing counts as applied.
- `store` in kay.config.ts is the one store of the app, `import { sqliteData } from 'kay/server'` then `store: sqliteData('data/app.sqlite')`, which keeps the data of every `session()`, the values of every `cached` and `live()`, the jobs of every queue and locked schedule, and the counts of every rate limit, each naming no `store` of its own, the members of presence rooms and the Web Vitals of `vitals()`, in one SQLite file, so replicas sharing it count together. `store: { sessions, cache, live, jobs, rates, rooms, vitals, notifications }` takes a `SessionStore`, a `CacheStore`, a `LiveStore`, a `JobStore`, a `RateStore`, a `RoomStore`, a `VitalsStore` and a `NotificationStore` of your own, each optional, Redis say; `rooms` is where `presence()` keeps who has a page open ([Presence](live-values.md#presence)). A `store` on a session, a `cached` call, a queue, a schedule or a limit wins, the proof-of-work solutions already used count there too, a `store.rates` needs `peek` for a limit counting only the posts that went through, kay's limits (actions, API routes, `rateLimit()`, proof of work, its own routes) count in memory when their rates store fails, and for ten seconds after one takes over 8 seconds ([Rate limits](rate-limits.md#reference)), and a `bun test` site keeps all of them in memory.
- `enqueue(payload, { key })` keeps one job per key: while a job of the queue with that key is waiting or running, it stores nothing and resolves with that job's id, whichever process holds it; the duplicate's payload is dropped, even one enqueued while the run goes, so an app that needs a rerun after it enqueues without a key. Once the job completed or was kept as failed the key is free. The key is a non-empty string, apart per queue, and needs a store with `state`, which `sqliteJobs`, `memoryJobs` and `pgJobs` have; a custom store without it throws a `config-invalid` error rather than not dedupe.
- `job(key)` or `job({ id })` resolves with `{ id, status, attempts, error? }`, `status` `'waiting'` (due, or waiting for a retry, its `error` the last run's), `'running'` or `'failed'`: the live job of the key, else its last failed one, `undefined` once it completed. An action returning it is what a page polls.
- `throw retryLater('30s')` from a handler (`retryLater(wait)` from `kay/server`, a positive duration) runs the job again after the wait without spending an attempt: the store's `release(id, until, runAt)` gives the claim's attempt back and makes it due then, so a job asking 10 times with `attempts: 3` is still waiting, logged at info, never `onFailed`. It repeats as long as the handler throws it, so one that should stop throws an error of its own; a store without `release` counts it as a failed attempt, with a warning.
- A handler is `(payload, signal, job)`: `job.id`, `job.attempts` (runs started, this one included) and `job.progress(value)`, which reports how far the run is, any devalue value, typed by `queue<Payload, Progress>`'s second argument. Reports are written in the background, one write at a time with the latest waiting, so reporting per item is cheap; `job(key)` reads the latest back as `progress` while the job runs, after it failed too, and a retried job's next claim clears it. A report after the run ended is dropped, as the store writes it only while the run's hold is the job's; a failed write is logged, not thrown. A store without `progress` logs once that nothing is kept.
- To show it, an action returns `job(key)` and a page or island polls it, as `export const syncState = action(async () => sync.job('anilist'))` called from an island: kay adds no route of its own, so the app decides who may see a job. The method is `job`, not `state`, which Elysia's own `.state()` already is.
- `live: true` on a queue lets `jobs<Payload, Progress>(name)` from `kay` read its waiting and running jobs in an island, the earliest due first, 100 at most: `{ id, key?, status: 'waiting' | 'running', attempts, runAt, error?, progress?, payload }`. `live: (payload, { key, error, progress }) => shown` sends `{ id, status, attempts, runAt, payload: shown }` alone, so a secret in the payload, the key or a run's error stays on the server; a job whose function throws is left out of the list, logged once. The page proves the queue it read as any live value ([Live values](live-values.md#live-values)), so whoever may render the page may follow the list, its guard deciding; a queue without `live` cannot be read, a `config-invalid` error at the render. The process changing a job tells its tabs within 50 ms, a burst of changes read once; one a tab follows the list through reads the store again every second, which is how what another worker or replica did reaches it. A render after a change, or of a list older than a second, reads it again: at once from `memoryJobs` and `sqliteJobs`, while a render on `pgJobs` or a store answering with promises shows the list as last read, the page's connection then bringing it up to date. A `JobStore` may have `live(queue, now, limit?)`, the waiting and running jobs with their status in one query, as `sqliteJobs`, `memoryJobs` and `pgJobs` do; a store without it is listed with `jobs` and asked `state` job by job. No start time is kept: `status` and `attempts` tell a run started. A `workflow()` has no `live`.
- Under `bun test` the default is in memory.
- Each job runs in one process.
- The payload goes through devalue, as cached values do: dates, maps and sets survive, a function or a class instance throws from `enqueue`.
- A run that throws is retried: `backoff` after the first failure, 10 seconds by default, twice as long after each next one, until `attempts` runs in all, 5 by default, each failure retried logged as a one-line warning with its attempt, its wait and the error's message.
- The last failure keeps the job as failed, logs it with its stack and hands `{ payload, error }` to `onFailed`; `failed()` lists the failed jobs, oldest first.
- `lazy: true` starts no worker with the server: the first `enqueue`, or `queue.activate()`, does, so a queue an app may never use has no idle poll; a job already stored waits until then (kayjs-mail's list queue).
- A failed job is kept 30 days from when its last attempt was due, payload included, then dropped by the workers, and by any `enqueue`, `failed()` or `remove()` of the queue in a process running none; `keepFailed` sets another duration, or `false` to keep it until removed. `redact(payload)` gives what a job keeps in place of its payload once it is given up, such as a mail without its body; `onFailed` still gets the whole payload. A custom `JobStore.fail(id, error, payload?)` stores that payload, and a store ignoring it keeps the job whole.
- `remove(id)` removes a job, and `remove(match)` every waiting or failed job whose payload `match` returns true for, such as a person's mails once they asked to be erased, resolving with how many went; an app's own `JobStore` takes a function only when it has `jobs(queue)`.
- An idle queue looks at the store from one worker, which is how a job another process enqueued is noticed: 1 second after a job, then twice as long after each empty look up to `idlePoll`, 10 seconds by default, so such a job waits 10 seconds at worst. A job enqueued in this process, or delayed to a time the store knows, still runs at once, and a retry is picked up when due. `idlePoll: '1s'` looks every second as the queue did before 1.45, `'30s'` asks the database less often; it takes at least `1s`. A custom `JobStore` may have `purge(queue, before)` to drop the expired failed jobs in one call.
- A store that fails, a SQLite file locked past its timeout say, is logged once as the outage starts and once as it ends, its workers asking it again later and later meanwhile, up to a minute apart.
- A handler takes `(payload, signal, job)`, `job` below: the `AbortSignal` aborts at `lostAfter`, so a handler passing it on stops instead of running beside the retry, and as the server stops, when a job it gives up on is released with `release(id, until)` of the `JobStore`, clearing the hold only while `until`, the one it was claimed with, is still the job's (optional): back without waiting out `lostAfter`, its attempt not counted, instead of held until `lostAfter` and retried after its backoff. Without `release` the job is retried as before.
- A process that dies running a job leaves it held: it runs again once `lostAfter` has passed since it started, 10 minutes by default. A run still going as `lostAfter` ends counts as a failed attempt, so its worker moves on, its handler's signal aborted, so a handler ignoring it runs on beside the retry, and a job longer than `lostAfter` needs a longer one, and a job whose process died during each of its `attempts` is kept as failed without running again, rather than crash every process that takes it.
- `drain()` runs every job whose time has come, here and now, until none is left, and waits for a run a worker already took (up to its `lostAfter` for one that never ends), except inside a job, which includes work the job spawned (a timer, a promise left running) and then does not wait, and a run counts once however many drains waited for it; in tests `site.runJobs()` from `kay/test` does it for every queue.
