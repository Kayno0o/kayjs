# Project setup and commands

## Project setup

kay is published as `@kaynooo/kayjs` to the registry at `https://git.kaynooo.fr/api/packages/kaynooo/npm/` and installed under the name its imports use: `"kay": "npm:@kaynooo/kayjs@~<version>"` in `package.json`, a tilde since a minor release may break what the one before it took, and a major is a rewrite, with `@kaynooo:registry=https://git.kaynooo.fr/api/packages/kaynooo/npm/` in the project's `.npmrc`. `bunx -p @kaynooo/kayjs kay new my-app` writes a project that already checks, builds and runs, both of those included: this setup, a layout, a page, a `_404.kay` and islands, or only what is picked of them (see [Commands](#commands) for the presets and features).

kay runs on Bun 1.4.3 or later, as its `engines` says: the CLI and `pages()` refuse an older one, naming its version, its path and the fix, `bun update bun` when it is the project's npm `bun` package, which a plugin's peer dependency installs and package scripts run ahead of the system Bun.

A folder of the project holding its own `package.json` or `kay.config.ts`, such as a workspace package or a second kay app, is a project of its own: `kay check` and `kay build` leave its files out of the app's, and the app reaches a package there through `node_modules`, as it would one installed.

By hand, the server entry is:

```ts
import { Elysia } from 'elysia'
import { pages } from 'kay/server'

export const app = new Elysia()
  .get('/feed.xml', feed)
  .use(await pages())
  .listen(3000)
```

Exporting `app` lets links and redirects point at the app's own GET routes, such as `/feed.xml`, which `kay check` otherwise reports as served by no page, and types `ctx.locals` (see [Locals](server.md#locals)). An entry `kay check` does not read registers it instead: `declare module 'kay' { interface Register { app: typeof app } }`.

Project settings live in an optional `kay.config.ts` at the root, read by `pages()` and every command; options passed to `pages()` or `testSite()` win over it key by key, an `undefined` option leaving the file's value, and in an executable `kay build --compile` wrote, the root, routes and public directory it was built with win over both. It must `export default` its config, or the command fails with a message saying so.

```ts
import { defineConfig } from 'kay/server'

export default defineConfig({
  routes: 'src/routes',
  lang: 'en',
  minify: true,
  prefetch: 'moderate',
  plugins: [],
})
```

A directory inside the project holding a `kay.config.ts` of its own, such as an example app or a documentation site, is another project: its components are never the outer one's islands, and it checks and builds from its own root.

`extensions` lists what libraries add to the app, one value each, such as `extensions: [authPages()]`: pages laid over `src/routes` and API modules over `src/api` under a prefix, message catalogs under `src/messages`, an app file at the same path or an app key winning, config laid under the app's, such as Bun plugins or head tags (see [Extensions](components.md#extensions)), and a hook rewriting each prerendered page (see [Page hooks](routing.md#page-hooks)).

`minify` is on for `kay build` unless set to `false`, and off for `kay dev` and a server bundling at boot unless set to `true`. `lang`, the `<html lang>` of every page when `i18n` is not set, defaults to `en`.

Every page carries speculation rules, which the swap replaces on pages shipping its script (see [Navigation](islands.md#navigation)): Chromium prefetches the page a link points at once it is hovered (`prefetch: 'moderate'`), on press with `'conservative'`, as soon as it can with `'eager'`, never with `false`. A link that changes something on GET, such as a logout, takes `data-no-prefetch`. A stylesheet holding `@view-transition { navigation: auto; }` animates from page to page where the browser supports it, swaps included; `kay new` writes one inside `@media (prefers-reduced-motion: no-preference)`.

`pages()` also takes `root`, `dev` (default: `NODE_ENV` is `development`) and `prebuilt` (default: `NODE_ENV` is `production`), which serves what `kay build` wrote instead of bundling at boot. A `.ts` file imports a component as `import Card from './card.kay'`, typed through the generated `.kay/types` tree. `.kay/` also holds the client build and the compile cache. List it in `.gitignore`. `tsconfig.json` extends kay's, which merges that tree with the sources and is as strict as kay itself:

```json
{ "extends": "kay/tsconfig.json" }
```

It includes `src`, `tests`, the `*.config.ts` files beside it, such as `kay.config.ts`, `eslint.config.ts` and `pg-orm.config.ts`, and `.kay/types`, relative to the project's tsconfig. A project adds its own `compilerOptions` beside `extends`, and an `include` of its own replaces kay's, so it lists `.kay/types` again; one setting up its tsconfig by hand needs `"jsx": "preserve"`, `"jsxImportSource": "kay"`, `"module": "Preserve"`, `"moduleResolution": "bundler"` and `"rootDirs": [".", ".kay/types"]`.

`kay/html`, `kay/dom`, `kay/island`, `kay/await`, `kay/client`, `kay/internal` and `kay/internal/server` are what compiled `.kay` files and kay's generated entries import: the compiler's output contract rather than API, free to change in any release, never imported by an app.

## Commands

- `kay new <dir> [--kay <dependency>] [--template blank|server|site|app] [--with <features>] [--without <features>] [-y]`: scaffold a project in an empty directory. A project is a set of features: `server` (an Elysia server; off, a static site), `starter` (a header, a skip link, a `_404.kay`, a home page greeting from the server with a counter island), `tailwind` (Tailwind through `bun-plugin-tailwind` over the Catppuccin Mocha palette; off, the markup carries no classes), `accents` (an accent picker in the header, kept in a cookie, which needs `starter` and `tailwind`), `eslint`, `tests`, `ci` (the Forgejo workflow below), `docker` (the container below), `auth` (the app's sessions, sign-in and members, which needs `server`) and `ws` (the app's API module and websocket island, shown on the home page, which needs `server`). A preset names a set: `blank` none, one layout and one bare page built as a static site; `server`, `site` and `app` as described below. Run in a terminal with none of `--template`, `--with`, `--without` or `-y`, it asks for a preset, then shows its features as a checklist, checking a feature checking what it needs and unchecking one unchecking what needs it; otherwise it takes `--template`, `server` by default, adds the comma-separated `--with` features and drops the `--without` ones, and refuses a feature listed in both, or one missing what it needs (`kay: accents needs tailwind: add --with tailwind, or drop it with --without accents`); every project has the `.npmrc` naming the registry kay comes from. The `server`, `site` and `app` presets have a layout with `seo` defaults and a skip link, a header with an accent picker over the Catppuccin Mocha palette, kept in a cookie, Tailwind through `bun-plugin-tailwind`, and Tabler icons. `server`, the default, is an Elysia server, with a `Dockerfile` and `compose.prod.yaml` running the executable `bun run compile` makes. `site` is a static site whose `bun run build` runs `kay build --static`, its pages showing the default accent until the picker hydrates, since no server reads the cookie, with a Forgejo Pages workflow publishing `dist` to the `gitea-pages` branch under `/<owner>/<repo>`, its `SITE_URL` a placeholder to replace with the host the Forgejo instance publishes Pages on, and a `Dockerfile` serving it with nginx instead. `app` is the server with sessions, a sign-in action keeping its members in Postgres through `@kaynooo/pg-orm`, a guarded `/account` section, an API module and an island over its websocket, its session secret and development database written to a `.env` git ignores, `.env.test` holding a test-only secret and the test database, and `.env.example` naming what production sets; `docker compose up -d --wait` starts the database `compose.dev.yaml` describes, `bun run db:migrate` applies `migrations/`, `bun run db:generate` writes the next migration from the tables in `src/db/`, its `bun run test` gives each test file a copy of the migrated, seeded database (see [Testing](testing.md)), its workflow runs Postgres as a service, and `compose.prod.yaml` runs the database and a one-shot service applying the migrations before the app; `--kay` sets the `kay` dependency, by default `npm:@kaynooo/kayjs@~<its version>`, or a packed copy when run from a checkout of kay. The package is named after the directory, lower case with other characters turned into `-`. Every template's `tsconfig.json` adds `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride` and `noFallthroughCasesInSwitch` to `strict`, as kay does itself, so an optional field passed `undefined` must say `?: T | undefined`; `server` and `app` carry a Forgejo workflow checking, linting and testing the project on every push, and the `site` workflow tests it before building, which checks it, then lints it (see [Linting](checks.md#linting)). Every project also has an `AGENTS.md` pointing coding agents at kay's docs for the installed version, through a `@node_modules/kay/llms.txt` line Claude Code expands at the start of a session, and naming the checks its scripts run; a project made before it adds it by hand.
- `kay dev [dir] [--entry <file>] [--port <port>] [--inspect[=<address>]] [--open]`: run the server entry (default `src/server.ts`) of the project in `dir`, or, with no file there, as in a `site` project, a server of kay's own serving its pages on `PORT`, 3000 by default, until a `src/server.ts` is written, the current directory by default, where a file given instead of `dir` is taken as the entry, and `--entry` is relative to the current directory, as `build`'s is, with `NODE_ENV=development`, and `PORT` set to `--port` when given, over the shell's and the `.env`'s, which a server reading `PORT` listens on; a port another process holds moves the server to the next free one, however the server picked it, `--port` included, the ready line naming the port in use, and every restart keeps the port it moved to; `--inspect` opens Bun's debugger in every server it runs, at `ws://localhost:6499/kay` or the port, host and port, or address given, port 0 taking a free one, on that one address across restarts so a debugger reconnects, printed once under the ready line with its `debug.bun.sh` link, `kay dev` listening there itself and passing each connection on to the server running, whose connection closes when it restarts, an address another process holds, at `localhost` on either loopback address, stopping `kay dev`; `--open` opens the address in the browser, the command `BROWSER` names or the system's, once the first server listens, restarting it on every change but to tests (`tests/`, `test/`, `e2e/`, `__tests__/`, and `*.test.*` and `*.spec.*` scripts anywhere) and to root files no server reads, such as a README, a LICENSE or a justfile, or to the backup, swap and temporary files editors write beside a source, one save restarting once however the editor writes it; open pages refresh by themselves, an edit to `.css` files alone restarts nothing and swaps the new stylesheets into the open pages, and a project that fails to compile shows its errors in the browser. A problem kay recovers from in the browser, such as an island that did not match its server markup or had no client chunk, or a message no locale has, shows in a panel at the bottom of the page as well as in the console, until dismissed or the page is left; production pages never carry it. Every page lists there too what `kay check` reports of the project's `.kay` files without type checking, such as an `img` without `alt`, an unread prop or a browser global read while rendering; type errors and unchecked links still wait for `kay check` or the editor. It lists as well each accessibility rule the rendered page breaks, such as text too faint on its background, as axe-core finds it once the page settled (see [Checks and lints](checks.md#checks-and-lints)). When only island components changed, an open page swaps each edited island in place, and each island rendering it inside, instead of reloading: the rest of the page, its other islands and its form fields stay as they were. The swapped island is built afresh, so what it does not hold in signals, such as an unbound input's text or the focus inside it, starts over; the signals its script creates keep their values, matched in the order it creates them, until one whose initial value is of another kind, as after adding a signal before it. Signals made inside a `for` row, an `if` or `await` block, or by kay itself start afresh; two signals of one kind swapped in the script trade values. A change to anything else, a page, a layout, a static component, a `.ts` module or a deleted source file, or an island edit that cannot swap in, refreshes the open page through the page swap once the server restarted, as `refresh()` does: the scroll, the islands whose props did not change and their state stay, and the rest of the page is rendered afresh. When the browser build changed under the page, as after a new island or an edit to a module islands share, the swap loads the page fully rather than run old code beside new, as a server that failed to boot always does. A page without the page swap (`navigation: false`) keeps the server render it loaded with and, once the server restarted, applies only what changed between it and the new render to the page: a node whose markup did not change stays as it is, with the classes, the transitions, the focus and the scroll scripts gave it, and an edited element has its attributes, text and children changed in place, a class by its names so one a script added stays. The page loads fully instead when that cannot apply, as when an island, a script, the `html` attributes or a streamed `await` block changed, or the page holds something its render did not. None of it is in a production build. Island chunks carry source maps, so the browser's devtools show and break on `.kay` lines. The next server process waits with kay already loaded and its `.kay` loader registered for the project with the settings of its `kay.config.ts`, so what the entry imports before it calls `pages()`, such as a mailer rendering `.kay` mails, loads `.kay` files, `~icons` and `import.meta.glob` as pages do, a `pages()` naming another root or other settings starting the loader over; compiled files are kept in `.kay/cache`, so a restart compiles only the file that changed. `kay dev` builds the browser code itself while the server boots, in a process it keeps from one change to the next, and the server reads that build as a production server reads `kay build`'s; an edit builds again only what it reaches: the islands when it touched a module of theirs or added or removed one, the stylesheets when it touched a stylesheet, the pages, a page's imports or, with a config plugin such as Tailwind, the classes, a word Tailwind makes no class of, as in prose, leaving the stylesheets as they are, so a change to a server module restarts the server alone. A `pages()` given options for the browser build that `kay.config.ts` does not hold bundles its own as it boots, with a warning, so those options belong in `kay.config.ts`. That browser build goes to `.kay/dev`, not `.kay/client`, so a `kay build` or a test run beside it leaves the files its pages link in place. A change to a file at the project root, such as `.env` or `package.json`, starts a fresh process, which reads the new `.env` values (variables set in the shell still win, unless they equal the file's value). The terminal shows the address of the first server the entry starts once, as `kay dev: http://localhost:3000 (ready in 412 ms)`, or `(ready in 412 ms, 3000 was in use)` when it moved, then one line per restart, as `14:02:31 src/routes/index.kay: restarted in 58 ms`, with `, now on <address>` when the address changed, or per stylesheet edit, as `14:02:47 src/app.css: stylesheets swapped in 24 ms`, and `the server exited with code 1, waiting for a change` when the server exits on its own; kay's own start line, `kay: listening on <address>, ...`, only shows in production, and an entry's own `console.log` of `Listening on <that address>`, as older templates printed, is left out. Under `kay dev`, every element a `.kay` template writes, but the head's, carries `data-kay-src="<file>:<line>:<column>"`, and every page loads the inspector: holding Alt outlines the element under the pointer with that position, from the moment Alt is pressed, Alt+click opens it in the editor, and a button at the bottom left, shown when the page has islands, lists each island's component (a click opens it) with the values its signals hold now, numbered in the order its script creates them, refreshed twice a second. The editor is `KAY_EDITOR` (a command, getting the position the way the editor among its words takes it, VS Code, Cursor, Zed, Sublime Text, JetBrains IDEs, code-server, Vim, Neovim and Helix included, as in `tmux new-window nvim`, else the file appended), else `VISUAL` or `EDITOR` when they name one of those that opens a window, else the first of them found on the `PATH`; on a Linux machine with no display, as one reached over SSH, only code-server counts, opening the file in its window already open on the project. With none, the page says so and the terminal prints the position; an editor command exiting with an error within 2 seconds prints its error in the terminal and the page says it failed. A server run any other way, `pages({ dev: true })` included, carries none of it, and neither does a production build.
- `kay build [dir] [-p tsconfig.json] [--no-check] [--analyze]`: bundle the islands and stylesheets for production, whatever `NODE_ENV` the shell holds and with none of the server's secrets, such as `preview.secret`, needed, minified, into `.kay/client` while checking the project as `kay check` does, `-p` naming the tsconfig as there; once the check passed, render the pages marked `prerender`, so no page, API module or guard runs before then. With the check on, a problem it reports, check-only ones included, or a build that fails leaves the last build in `.kay/client` as it was; `--no-check` skips the check and builds in place. Then start the server with `NODE_ENV=production`, as `kay start` does. Each page preloads the chunks of the islands it renders. kay's runtime, all any island uses of it included, is the one chunk a page loads first, so a page with islands loads that chunk and one per island, plus one for code several islands import. The build prints what that weighs, gzip then minified: the entry every page with an island loads, then what each island adds beyond it, the heaviest first; `--analyze` also names the five modules weighing most in each, a package's files counted as one, kay's runtime file by file. Every text file it writes, prerendered pages included, gets a brotli and a gzip copy, sent to a browser whose `Accept-Encoding` takes one, with `Vary: Accept-Encoding`; other responses go uncompressed, left to a proxy in front, unless `compress` is on.
- `kay build [dir] --compile <executable> [--entry src/server.ts]`: the same, then bundles the server entry, every page, layout, special page, guard and API module, `kay.config.ts` and the client build and public files into one executable, which runs from anywhere as the production server would: `PORT=8080 ./server`. It carries its code as bytecode, so it starts without parsing it. It reads nothing of the project from disk but a `.env` and `bunfig.toml` where it runs, as `bun` would, so a file a page reads at runtime by path, rather than importing it, is not in it; the root, routes and public directory it was built with win over the options given to `pages()`. `--compile` and `--entry` are relative to the current directory. The public directory cannot be named `client`. The executable carries `kay.config.ts` without its `plugins`, nor the imports and top-level declarations only they used, side effects included, so a build plugin such as Tailwind's, whose native addon loads from node_modules, never runs there; plugins set other than as a property of the object the file exports by default, or beside a spread, stay in, with a warning.
- `kay build [dir] --static [--outdir dist]`: the same, then writes the whole site to `--outdir` for a host with no server; see [Static export](routing.md#static-export).
- `kay start [dir] [--entry <file>] [--port <port>]`: serve the last `kay build` as the deployed server would, with `NODE_ENV=production`: the executable `--compile` wrote when that build made one (a later build without `--compile` drops it; one older than the build warns), else the server entry, else, in a project with none, kay's own server of its pages. It refuses without a build in `.kay/client`, and warns when a file the server or its build reads changed since, naming the latest; env files are left for the server to read as Bun does under `NODE_ENV=production`, `.env.production` and `.env` both, so a value only `.env` holds reaches it, the shell's variables winning. `--entry` runs another entry, relative to the current directory; `--port` sets `PORT`, over the shell's and the env files', 3000 otherwise. Ctrl-C, `SIGTERM` and `SIGHUP` reach the server once, sent to the group or to `kay start` alone, which waits for it to drain, a second Ctrl-C stopping it at once; `SIGQUIT` is passed on and ends it at once (131). The server runs in a process group of its own: Ctrl-Z suspends `kay start` alone, and once `kay start` is gone, as after a `SIGKILL` to the group, a kay server notices within a second and drains as on `SIGTERM`, or stops once booted when it was gone already; it exits with the server's code, 0 when the server ended on a stop signal it passed on, 128 plus the signal's number when it died of another. The `start` script `kay new` writes runs it.
- `kay check [dir] [paths...] [-p tsconfig.json] [--entry <file>] [--deny-warnings] [--fix] [--only <group>] [--format text|github|json] [--watch]`: type-check the project, `.kay` files included; the first path is the project when it is a directory holding a `kay.config.ts`, `package.json` or `tsconfig.json`, or any directory outside the current directory, so a directory given first to narrow the report must be neither; the other paths, files or directories relative to the current directory, a symlink read as what it points to, narrow the report, and `--fix`, to the problems in them, the project still checked as a whole, and one outside the project fails the check; `--watch` checks again on every change, tests included, each check a `kay check` of its own, so an edit to `kay.config.ts` counts and a check that cannot run, or exits before reporting, leaves the watch going, clearing the previous report in a terminal, and an interrupt or a closed terminal stops the check running and what it started, a second interrupt killing them; `-p` is relative to `dir`, and a tsconfig that is missing or matches no files fails the check. `--entry` names the server entry whose `app` types `ctx.locals` and the app routes, `src/server.ts` by default, as `kay build --entry` does (see [Locals](server.md#locals)). It fails on errors, and on warnings too with `--deny-warnings` (see [Lints and warnings](checks.md#lints-and-warnings)). `--fix` first applies the quick fixes that change nothing else, removing an unread prop or writing `onclick` as `onClick`, then reports what is left; the others, such as a key or a `maxLength` to choose, stay the editor's. `--only seo` prints one group's lints alone, as an audit (see [Lints and warnings](checks.md#lints-and-warnings)). `--format github` prints each problem as a workflow command, `::error file=...,line=...,col=...::message`, which GitHub and Forgejo Actions show on the diff, as the CI `kay new` writes does, its `file` relative to `GITHUB_WORKSPACE`, the repository's root, when set; `--format json` prints `{ errors, warnings, problems }` on stdout, each problem's `file` relative to the current directory with its `line`, `column`, `endLine`, `endColumn`, `severity`, `code` and `message`; a check that cannot run, on a path that does not exist or a `kay.config.ts` that does not load, prints one error in the format too, with no `file` but where a config does not parse; the exit code is the same in every format. It also reports what the server would refuse when it boots, with the same functions: two pages serving one path, a redirect from a path a page serves or with syntax the router refuses, a page under a locale's prefix, a public file a page serves, two files whose actions share a URL (`a b.kay` and `a_b.kay`), a `base`, `site` or `shutdownTimeout` it cannot read, a collection feed without `site`, and a guard, API module or matcher whose default export is not a guard, an Elysia instance or a function. `kay build` reports them as it checks, and the editor after a save or a change on disk.
- `kay routes [dir]`: list the routes the project serves, without running a page or a guard: each page's pattern with its matchers, `/items/:id=integer`, and file, once per locale's path (`/about`, `/fr/a-propos`), with its layouts and guards, outermost first, `prerendered` with `prerender: true` or a server island, `prerendered as its prerender setting lists` with a list or a function, `open` with `guards: false` and the 403 `requireGuards` gives one with no guard; each action, endpoint, API module route with its method, `WS` and `OPTIONS` included, and a library's with the guards of its own directory (API modules are imported, as only they know their routes, so their top-level code runs: what it writes to stdout, through the console or `process.stdout`, goes to stderr, and one that fails to load or calls `process.exit()` is listed by its mount with why), the routes of an extension's `server` given as an Elysia instance, each redirect and collection feed; and kay's own routes the config turns on, such as `/_kay/health`, the favicons and the sitemap. What the server entry adds, as a `.use(auth.plugin)`, and an extension's `server` given as a function are only known as the server starts: a last line names them, unlisted.
- `kay explain [lint|group]`: list the lints with their groups and default levels, or a group's, or print one with an example it reports and the same written right.
- `kay fmt [paths...] [--check]`: format `.kay` files; `--check` lists unformatted files and fails.
- `kay migrate astro [dir] [--out <dir>]`: translate an Astro project's `.astro` files into `.kay` ones, `src/pages` into `src/routes` (`404` as `_404`), components and layouts kept in their folder with kebab-case names and the imports of them rewritten, and `src/content.config.ts` into kay's, its zod schemas written in `t`. The frontmatter becomes the fence, a page's `--- server` with `Astro.url`, `params`, `cookies` and `redirect` read from `ctx`, `Astro.props` becomes `props<Props>()`, and the markup the indented template: static classes as the `.class` shorthand, `class:list` as `class`, `&&`, ternaries and `.map` as `if` and `for`, slots as `slot` and `@name` blocks, `client:idle` and `client:visible` as `hydrate`, `set:html` as `innerHTML` through `trustHtml`, a layout's `head` as a `head` block. It writes into the project, or into `--out`, never over a file that exists, formats what it writes, and lists what it could not translate at its line in the Astro file: a script Astro bundles, an `await` or `Astro.url` in a component, an endpoint, markup written another way, each commented out under a `// kay migrate:` line where it stays in the code, and Tailwind 3, as kay builds with Tailwind 4. A `--out` directory with no `package.json` gets the kay project around the pages, as `kay new` writes it without its home page, layout and stylesheet: a `package.json` with kay's scripts and the Astro project's packages, Astro's own left out, a `kay.config.ts` with the `site` and `base` of the Astro config and the layout's `<html lang>`, without `seo` defaults since the pages write their own head, a `tsconfig.json` keeping its `paths`, a server entry when the Astro config renders on demand (`output: 'server'` or an `adapter`), a static site otherwise, and Tailwind, ESLint, the Forgejo workflow and the Dockerfile when the Astro project had them; its other files under `src` and `public` are copied as they are, but for `src/env.d.ts`, which only Astro reads, those beside the pages moving with them into `src/routes`, where kay routes only `.kay` and endpoint files. A Markdown page in `src/pages` is listed, to become a content collection's entry, and so is a `site` or `base` written as anything but a string. Migrated in place, the Astro project's `package.json` stays as it is, listed with the Astro packages to remove, and the `lang`, `site`, `base` and tsconfig `paths` are listed to carry over by hand.
- `kay lsp --stdio`: the language server behind the editor extension in `editors/vscode`: errors, hover, completion with auto-import, signatures, definitions, references, rename, quick fixes and formatting in `.kay` files. An import it adds goes in the fence the name is used from, the server fence for server code and the component script otherwise, made if missing. Renaming a server value renames its reads in the template, and renaming a destructured prop renames it in every parent passing it.

Every command prints its usage for `--help` or `-h`, and refuses an option or argument it does not take. `kay fmt` refuses a path that is missing or is neither a directory nor a `.kay` file.

The TextMate grammar the extension highlights `.kay` files with ships as `kay/kay.tmLanguage.json`, for a highlighter such as Shiki: register it as `{ ...grammar, name: 'kay', embeddedLangs: ['typescript'] }`.
