# Project setup and commands

## Project setup

kay is published as `@kaynooo/kayjs` to the registry at `https://git.kaynooo.fr/api/packages/kaynooo/npm/` and installed under the name its imports use: `"kay": "npm:@kaynooo/kayjs@~<version>"` in `package.json`, a tilde since a minor release may break what the one before it took, and a major is a rewrite, with `@kaynooo:registry=https://git.kaynooo.fr/api/packages/kaynooo/npm/` in the project's `.npmrc`. `bunx -p @kaynooo/kayjs kay new my-app` writes a project that already checks, builds and runs, both of those included: this setup, a layout, a page, a `_404.kay` and islands (see [Commands](#commands) for the templates). By hand, the server entry is:

```ts
import { Elysia } from 'elysia'
import { pages } from 'kay/server'

export const app = new Elysia().get('/feed.xml', feed).use(await pages()).listen(3000)
```

Exporting `app` lets links and redirects point at the app's own GET routes, such as `/feed.xml`, which `kay check` otherwise reports as served by no page, and types `ctx.locals` (see [Locals](server.md#locals)). An entry `kay check` does not read registers it instead: `declare module 'kay' { interface Register { app: typeof app } }`.

Project settings live in an optional `kay.config.ts` at the root, read by `pages()` and every command; options passed to `pages()` or `testSite()` win over it key by key, an `undefined` option leaving the file's value, and in an executable `kay build --compile` wrote, the root, routes and public directory it was built with win over both. It must `export default` its config, or the command fails with a message saying so.

```ts
import { defineConfig } from 'kay/server'

export default defineConfig({ routes: 'src/routes', lang: 'en', minify: true, prefetch: 'moderate', plugins: [] })
```

A directory inside the project holding a `kay.config.ts` of its own, such as an example app or a documentation site, is another project: its components are never the outer one's islands, and it checks and builds from its own root.

`minify` is on for `kay build` unless set to `false`, and off for `kay dev` and a server bundling at boot unless set to `true`. `lang`, the `<html lang>` of every page when `i18n` is not set, defaults to `en`.

Every page carries speculation rules, which the swap replaces on pages shipping its script (see [Navigation](islands.md#navigation)): Chromium prefetches the page a link points at once it is hovered (`prefetch: 'moderate'`), on press with `'conservative'`, as soon as it can with `'eager'`, never with `false`. A link that changes something on GET, such as a logout, takes `data-no-prefetch`. A stylesheet holding `@view-transition { navigation: auto; }` animates from page to page where the browser supports it, swaps included; `kay new` writes one inside `@media (prefers-reduced-motion: no-preference)`.

`pages()` also takes `root`, `dev` (default: `NODE_ENV` is `development`) and `prebuilt` (default: `NODE_ENV` is `production`), which serves what `kay build` wrote instead of bundling at boot. A `.ts` file imports a component as `import Card from './card.kay'`, typed through the generated `.kay/types` tree. `.kay/` also holds the client build and the compile cache. List it in `.gitignore`. `tsconfig.json` extends kay's, which merges that tree with the sources and is as strict as kay itself:

```json
{ "extends": "kay/tsconfig.json" }
```

It includes `src`, `tests`, the `*.config.ts` files beside it, such as `kay.config.ts`, `eslint.config.ts` and `pg-orm.config.ts`, and `.kay/types`, relative to the project's tsconfig. A project adds its own `compilerOptions` beside `extends`, and an `include` of its own replaces kay's, so it lists `.kay/types` again; one setting up its tsconfig by hand needs `"jsx": "preserve"`, `"jsxImportSource": "kay"`, `"module": "Preserve"`, `"moduleResolution": "bundler"` and `"rootDirs": [".", ".kay/types"]`.

`kay/html`, `kay/dom`, `kay/island`, `kay/await`, `kay/client`, `kay/internal` and `kay/internal/server` are what compiled `.kay` files and kay's generated entries import: the compiler's output contract rather than API, free to change in any release, never imported by an app.

## Commands

- `kay new <dir> [--kay <dependency>] [--template server|site|app]`: scaffold a project in an empty directory. Every template has a layout with `seo` defaults and a skip link, a header with an accent picker over the Catppuccin Mocha palette, kept in a cookie, Tailwind through `bun-plugin-tailwind`, and Tabler icons. `server`, the default, is an Elysia server, with a `Dockerfile` and `compose.prod.yaml` running the executable `bun run compile` makes. `site` is a static site whose `bun run build` runs `kay build --static`, its pages showing the default accent until the picker hydrates, since no server reads the cookie, with a Forgejo Pages workflow publishing `dist` to the `gitea-pages` branch under `/<owner>/<repo>` and a `Dockerfile` serving it with nginx instead. `app` is the server with sessions, a sign-in action keeping its members in Postgres through `@kaynooo/pg-orm`, a guarded `/account` section, an API module and an island over its websocket, its session secret and development database written to a `.env` git ignores, `.env.test` holding a test-only secret and the test database, and `.env.example` naming what production sets; `docker compose up -d --wait` starts the database `compose.dev.yaml` describes, `bun run db:migrate` applies `migrations/`, `bun run db:generate` writes the next migration from the tables in `src/db/`, its `bun run test` gives each test file a copy of the migrated, seeded database (see [Testing](testing.md)), its workflow runs Postgres as a service, and `compose.prod.yaml` runs the database and a one-shot service applying the migrations before the app; `--kay` sets the `kay` dependency, by default `npm:@kaynooo/kayjs@~<its version>`, or a packed copy when run from a checkout of kay. The package is named after the directory, lower case with other characters turned into `-`. Every template's `tsconfig.json` adds `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride` and `noFallthroughCasesInSwitch` to `strict`, as kay does itself, so an optional field passed `undefined` must say `?: T | undefined`; `server` and `app` carry a Forgejo workflow checking, linting and testing the project on every push, and the `site` workflow tests it before building, which checks it, then lints it (see [Linting](checks.md#linting)).
- `kay dev [dir] [--entry <file>]`: run the server entry (default `src/server.ts`) of the project in `dir`, or, with no file there, as in a `site` project, a server of kay's own serving its pages on `PORT`, 3000 by default, until a `src/server.ts` is written, the current directory by default, where a file given instead of `dir` is taken as the entry, and `--entry` is relative to the current directory, as `build`'s is, with `NODE_ENV=development`, restarting it on every change; open pages refresh by themselves, or only swap their stylesheets when nothing but `.css` files changed, and a project that fails to compile shows its errors in the browser. A problem kay recovers from in the browser, such as an island that did not match its server markup or had no client chunk, or a message no locale has, shows in a panel at the bottom of the page as well as in the console, until dismissed or the page is left; production pages never carry it. Every page lists there too what `kay check` reports of the project's `.kay` files without type checking, such as an `img` without `alt`, an unread prop or a browser global read while rendering; type errors and unchecked links still wait for `kay check` or the editor. When only island components changed, an open page swaps each edited island in place, and each island rendering it inside, instead of reloading: the rest of the page, its other islands and its form fields stay as they were. The swapped island is built afresh, so what it does not hold in signals, such as an unbound input's text or the focus inside it, starts over; the signals its script creates keep their values, matched in the order it creates them, until one whose initial value is of another kind, as after adding a signal before it. Signals made inside a `for` row, an `if` or `await` block, or by kay itself start afresh; two signals of one kind swapped in the script trade values. A change to anything else, a page, a layout, a static component, a `.ts` module or a deleted source file, or an island edit that cannot swap in, refreshes the open page through the page swap once the server restarted, as `refresh()` does: the scroll, the islands whose props did not change and their state stay, and the rest of the page is rendered afresh. When the browser build changed under the page, as after a new island or an edit to a module islands share, the swap loads the page fully rather than run old code beside new, as a page without the page swap (`navigation: false`) and a server that failed to boot always do. None of it is in a production build. Island chunks carry source maps, so the browser's devtools show and break on `.kay` lines. The next server process waits with kay already loaded, and compiled files are kept in `.kay/cache`, so a restart compiles only the file that changed. A change to a file at the project root, such as `.env` or `package.json`, starts a fresh process, which reads the new `.env` values (variables set in the shell still win, unless they equal the file's value).
- `kay build [dir] [-p tsconfig.json] [--no-check]`: bundle the islands and stylesheets for production, minified, into `.kay/client` while checking the project as `kay check` does, `-p` naming the tsconfig as there; once the check passed, render the pages marked `prerender`, so no page, API module or guard runs before then. With the check on, a problem it reports, check-only ones included, or a build that fails leaves the last build in `.kay/client` as it was; `--no-check` skips the check and builds in place. Then start the server with `NODE_ENV=production`. Each page preloads the chunks of the islands it renders. kay's runtime, all any island uses of it included, is the one chunk a page loads first, so a page with islands loads that chunk and one per island, plus one for code several islands import. Every text file it writes, prerendered pages included, gets a brotli and a gzip copy, sent to a browser whose `Accept-Encoding` takes one, with `Vary: Accept-Encoding`; other responses go uncompressed, left to a proxy in front, unless `compress` is on.
- `kay build [dir] --compile <executable> [--entry src/server.ts]`: the same, then bundles the server entry, every page, layout, special page, guard and API module, `kay.config.ts` and the client build and public files into one executable, which runs from anywhere as the production server would: `PORT=8080 ./server`. It carries its code as bytecode, so it starts without parsing it. It reads nothing of the project from disk but a `.env` and `bunfig.toml` where it runs, as `bun` would, so a file a page reads at runtime by path, rather than importing it, is not in it; the root, routes and public directory it was built with win over the options given to `pages()`. `--compile` and `--entry` are relative to the current directory. The public directory cannot be named `client`. The executable carries `kay.config.ts` without its `plugins`, nor the imports and top-level declarations only they used, side effects included, so a build plugin such as Tailwind's, whose native addon loads from node_modules, never runs there; plugins set other than as a property of the object the file exports by default, or beside a spread, stay in, with a warning.
- `kay build [dir] --static [--outdir dist]`: the same, then writes the whole site to `--outdir` for a host with no server; see [Static export](routing.md#static-export).
- `kay check [dir] [-p tsconfig.json] [--entry <file>] [--deny-warnings] [--fix]`: type-check the project, `.kay` files included; `-p` is relative to `dir`, and a tsconfig that is missing or matches no files fails the check. `--entry` names the server entry whose `app` types `ctx.locals` and the app routes, `src/server.ts` by default, as `kay build --entry` does (see [Locals](server.md#locals)). It fails on errors, and on warnings too with `--deny-warnings` (see [Lints and warnings](checks.md#lints-and-warnings)). `--fix` first applies the quick fixes that change nothing else, removing an unread prop or writing `onclick` as `onClick`, then reports what is left; the others, such as a key or a `maxLength` to choose, stay the editor's. It also reports what the server would refuse when it boots, with the same functions: two pages serving one path, a redirect from a path a page serves or with syntax the router refuses, a page under a locale's prefix, a public file a page serves, two files whose actions share a URL (`a b.kay` and `a_b.kay`), a `base`, `site` or `shutdownTimeout` it cannot read, a collection feed without `site`, and a guard, API module or matcher whose default export is not a guard, an Elysia instance or a function. `kay build` reports them as it checks; the editor does not, as it reads routes mid-edit.
- `kay explain [lint]`: list the lints with their default levels, or print one with an example it reports and the same written right.
- `kay fmt [paths...] [--check]`: format `.kay` files; `--check` lists unformatted files and fails.
- `kay migrate astro [dir] [--out <dir>]`: translate an Astro project's `.astro` files into `.kay` ones, `src/pages` into `src/routes` (`404` as `_404`), components and layouts kept in their folder with kebab-case names and the imports of them rewritten, and `src/content.config.ts` into kay's, its zod schemas written in `t`. The frontmatter becomes the fence, a page's `--- server` with `Astro.url`, `params`, `cookies` and `redirect` read from `ctx`, `Astro.props` becomes `props<Props>()`, and the markup the indented template: static classes as the `.class` shorthand, `class:list` as `class`, `&&`, ternaries and `.map` as `if` and `for`, slots as `slot` and `@name` blocks, `client:idle` and `client:visible` as `hydrate`, `set:html` as `innerHTML` through `trustHtml`, a layout's `head` as a `head` block. It writes into the project, or into `--out`, never over a file that exists, formats what it writes, and lists what it could not translate at its line in the Astro file: a script Astro bundles, an `await` or `Astro.url` in a component, an endpoint, markup written another way, each commented out under a `// kay migrate:` line where it stays in the code. The project's `package.json`, `kay.config.ts` and server entry are left to `kay new`.
- `kay lsp --stdio`: the language server behind the editor extension in `editors/vscode`: errors, hover, completion with auto-import, signatures, definitions, references, rename, quick fixes and formatting in `.kay` files. An import it adds goes in the fence the name is used from, the server fence for server code and the component script otherwise, made if missing. Renaming a server value renames its reads in the template, and renaming a destructured prop renames it in every parent passing it.

Every command prints its usage for `--help` or `-h`, and refuses an option or argument it does not take. `kay fmt` refuses a path that is missing or is neither a directory nor a `.kay` file.

The TextMate grammar the extension highlights `.kay` files with ships as `kay/kay.tmLanguage.json`, for a highlighter such as Shiki: register it as `{ ...grammar, name: 'kay', embeddedLangs: ['typescript'] }`.
