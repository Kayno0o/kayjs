# The dev server

## Common tasks

### Run the dev server

`kay dev` runs one server process for the whole session: a change to a template, island, loader or API route, to an entry of a content collection, or to a module only those import (the content config and what it imports included, unless a collection has a loader) imports what changed again in that process and swaps the routes in place, and only a change it cannot (the config, the entry, a module the entry or other code imports) starts a new process, from cold. So does a process that grew 64 MiB over its reloads (`KAY_DEV_RELOAD_GROWTH_MB` sets the MiB, and the app does not see it), or took 200 of them, as Bun caches the code of the ES modules it evaluates again, up to a cap that this growth reaches first. Each reload lets go of what the modules that run again opened: the `process.on` listeners, `setInterval` timers and `Bun.SQL` pools they created themselves, and the `sqliteRooms`, `sqliteCache`, `sqliteRates`, `sqliteJobs` and unnamed SQLite session stores, so an edit leaves one of each, not one more. What a library opens for them and a `bun:sqlite` `Database` stay open: open those in a module that does not run again, or close them in `onStop`. It refreshes the open pages and shows errors in the browser:

```sh
kay dev --port 4000 --open
```

## Reference

### `kay dev`

- `kay dev [dir] [--entry <file>] [--port <port>] [--host[=<address>]] [--inspect[=<address>]] [--open] [--format text|json] [--quiet]`:
  - Run the server entry of the project in `dir`, the current directory by default, with `NODE_ENV=development`. The entry is `src/server.ts` by default; a file given instead of `dir` is taken as the entry, and `--entry` is relative to the current directory, as `build`'s is.
  - With no entry file, as in a `site` project, a server of kay's own serves the pages on `PORT`, 3000 by default, until a `src/server.ts` is written.
  - `--port` sets `PORT`, over the shell's and the `.env`'s, and a server reading `PORT` listens on it. `HOST` is left out of the app's environment.
  - A port another process holds moves the server to the next free one, the ready line naming the port in use, and every restart keeps the port it moved to, unless `--port` or a `PORT` in the environment or `.env` asked for it: the server then fails to start, naming the port, rather than listen elsewhere;
  - A server naming no `hostname` listens on `localhost` alone, so nothing past this machine reaches it, unless `--host` opens it to the network (`--host` alone is `0.0.0.0`, `--host=<address>` one address), as `kay dev` in a container publishing its port needs;
  - A request whose `Host` is not `localhost`, a `*.localhost` name, an IP address or the site's host gets 421, as a page of another site renaming itself to this machine (DNS rebinding) would send it.
  - `--host` adds this machine's own name and `<name>.local` to those hosts. Other names, such as a tunnel's, go in `KAY_DEV_HOSTS`, comma-separated and without ports.
  - `--inspect` opens Bun's debugger in every server it runs, at `ws://localhost:6499/kay` or the port, host and port, or address given; port 0 takes a free one.
  - That address stays the same across restarts, so a debugger reconnects, and is printed once under the ready line with its `debug.bun.sh` link.
  - `kay dev` listens there itself and passes each connection on to the server running. A connection stays open across a reload and closes when the server restarts in a new process.
  - An address another process holds, at `localhost` on either loopback address, stops `kay dev`. An address past this machine is refused unless `--host` is given too.
  - A page reaches the debugger only from the dev server's own `localhost` origin or `debug.bun.sh`.
  - `--open` opens the address in the browser, the command `BROWSER` names or the system's, once the first server listens.
  - Every change reloads the server, but one to tests (a root `tests/`, `test/`, `e2e/` or a name joining them such as `tests-e2e/`, `__tests__/`, `*.test.*`, `*.spec.*` and `*.e2e.*` scripts anywhere, and a root `playwright`, `vitest`, `jest` or `cypress` config), to root files no server reads, such as a README, a LICENSE or a justfile, or to the backup, swap and temporary files editors write beside a source. One save restarts once, however the editor writes it.
  - A page whose server went away reconnects at once, slows to every 5 s after 10 s down (a proxy's 502 counts), and a hidden tab waits until shown.
  - Open pages refresh by themselves, an edit to `.css` files alone restarts nothing and swaps the new stylesheets into the open pages, and a project that fails to compile shows its errors in the browser, and in the terminal once as the server boots, formatted as `kay check` prints them; a request that throws prints its error in the terminal, its stack mapped to `.kay` lines.
  - A page that throws, with no `_error.kay`, or a server that failed to boot shows an error page following the system's light or dark theme: the message, the lines around where the project's own code threw, its frames, those of kay and the dependencies folded, and a Copy button for the message and stack;
  - Under `kay dev` each frame and compile error position opens in the editor on a click.
  - The dev tool, its tabs and the problems it lists are in [The dev tool](dev-tool.md).
  - When only island components changed, an open page swaps each edited island in place, and each island rendering it inside, instead of reloading: the rest of the page, its other islands and its form fields stay as they were.
  - The swapped island is built afresh, so what it does not hold in signals, such as an unbound input's text or the focus inside it, starts over; the signals its script creates keep their values, matched in the order it creates them, until one whose initial value is of another kind, as after adding a signal before it.
  - Signals made inside a `for` row, an `if` or `await` block, or by kay itself start afresh; two signals of one kind swapped in the script trade values.
  - A change to anything else, a page, a layout, a static component, a `.ts` module or a deleted source file, or an island edit that cannot swap in, refreshes the open page through the page swap once the server restarted, as `refresh()` does: the scroll, the islands whose props did not change and their state stay, a field the edit leaves as it was keeps what was typed into it (one the edit removed, renamed or gave another rendered value shows what the page renders), and the rest of the page is rendered afresh.
  - When the browser build changed under the page, as after a new island or an edit to a module islands share, the swap loads the page fully rather than run old code beside new, as a server that failed to boot always does.
  - A page without the page swap (`navigation: false`) keeps the server render it loaded with and, once the server restarted, applies only what changed between it and the new render to the page: a node whose markup did not change stays as it is, with the classes, the transitions, the focus and the scroll scripts gave it, and an edited element has its attributes, text and children changed in place, a class by its names so one a script added stays.
  - The page loads fully instead when that cannot apply, as when an island, a script, the `html` attributes or a streamed `await` block changed, or the page holds something its render did not.
  - None of it is in a production build.
  - Island chunks carry source maps, so the browser's devtools show and break on `.kay` lines.
  - A server process started from cold loads kay and registers its `.kay` loader for the project with the settings of its `kay.config.ts`, so what the entry imports before it calls `pages()`, such as a mailer rendering `.kay` mails, loads `.kay` files, `~icons` and `import.meta.glob` as pages do, a `pages()` naming another root or other settings starting the loader over;
  - Compiled files are kept in `.kay/cache`, so a restart compiles only the file that changed; `kay build` drops the entries of components and content files since deleted, and keeps the favicons it drew and the compressed copies of each file by content, drawing and compressing only what changed.
  - `kay dev` builds the browser code itself while the server boots, in a process it keeps from one change to the next, and the server reads that build as a production server reads `kay build`'s;
  - A start leaves the build an earlier run left in `.kay/dev` as it is when nothing it read has changed since: every source and file the build read, `package.json`, the lockfile, `kay.config.ts`'s client options, the versions of kay and Bun, and the build's own output; a source added, deleted or edited while `kay dev` was down, or written within two seconds before that build began, builds it again, and the first edit after such a start builds everything once; an edit `kay dev` took while it ran is told unchanged by its size and times alone.
  - An edit builds again only what it reaches: the islands when it touched a module of theirs or added or removed one, the stylesheets when it touched a stylesheet, the pages, a page's imports or, with a config plugin such as Tailwind, the classes, a word Tailwind makes no class of, as in prose, leaving the stylesheets as they are, so a change to a server module reloads the server alone.
  - A `pages()` given options for the browser build that `kay.config.ts` does not hold bundles its own as it boots, with a warning, so those options belong in `kay.config.ts`.
  - That browser build goes to `.kay/dev`, not `.kay/client`, so a `kay build` or a test run beside it leaves the files its pages link in place.
  - The first server starts once `kay.config.ts` is read, and the `.kay/types` tree is written when it listens (or after 3 s without), so the first page does not wait for it; a `kay.config.ts` that does not load still stops `kay dev` before any server starts.
  - A start whose root files (`kay.config.ts`, `package.json`, `.env*`, the lockfile) are as the last one left them takes the entry from `.kay/dev/config.json` and starts the server at once, while the types process reads the config; if it does not load, `kay dev` stops with the error, and if its `entry` differs, the server starts again on the right one.
  - A `kay.config.ts` edit starts the new server without waiting for the types tree to be written, and starts it again only when `entry` changed.
  - A project with pages starts its client builder with the first server instead of when the server asks for it.
  - The server imports its extension servers and lists its API modules while the browser build runs, and waits for the build only where it first reads it.
  - A change to a file at the project root, such as `.env`, starts a fresh process, which reads the new `.env` values (variables set in the shell still win, unless they equal the file's value).
  - An edit to `package.json` restarts only when a field Bun resolves with changed (`dependencies` and its kin, `imports`, `exports`, `workspaces`, `type`) and then starts the client builder and the types process again; a script, version or description edit does nothing, unless a source of the project names `package.json`, as `import { version } from '../package.json'` does, and then it is an edit of that module like any other.
  - The terminal shows the address of the first server the entry starts once, as `kay dev: http://localhost:3000 (ready in 412 ms)`, or `(ready in 412 ms, 3000 was in use)` when it moved, then one line per reload, as `14:02:31 src/routes/index.kay: reloaded in 58 ms` for a change the running process took in, or per restart, as `14:02:40 src/server.ts: restarted in 412 ms` for a new process, with `, now on <address>` when the address changed, or per stylesheet edit, as `14:02:47 src/app.css: stylesheets swapped in 24 ms`, and `the server exited with code 1, waiting for a change` when the server exits on its own; on a terminal, a restart or swap line the same as the one before, nothing printed between, is rewritten with a count, `(x3)`, unless the app printed between, though output it writes natively, bypassing `console` and `process.stdout`/`process.stderr`, is not seen; while piped every line stays; `--quiet` leaves out the keys line and the restart and stylesheet lines, a restart that moved the address excepted, and under `--format json` the same `restart` and `styles` events, a `restart` one carrying `reloaded: true` for a reload;
  - Under `--host` listening on every address, a second line names the address this machine is reached at on its network, as `kay dev: http://192.168.1.20:3000 on the network`. It prints piped too, and it names the first interface no container, bridge or VPN made, on Linux and macOS alike.
  - In a terminal, `kay dev` lists its keys under the ready line and reads them: `o` opens the address in the browser, `r` restarts the server in a new process, its line saying `r pressed`, `c` clears the screen and `q` or Ctrl+C quits, while Ctrl+Z reaches it as a key too and does not suspend it; piped, or under `--format json`, it reads no key and prints no such line.
  - kay's own start line, `kay: listening on <address>, ...`, only shows in production, and an entry's own `console.log` of `Listening on <that address>` is left out.
  - `--format json` prints each of those as one JSON object per line on stdout, `{ "event": "ready", "time", "url", "ms" }`, with `network` under `--host`, then `restart` (`changed`, the files, `ms`, `url`), `styles`, `exit` (`code`), `debugger`, `no-browser` and `builder-exit`, and an `error` event for each error `.kay/dev/errors.json` lists, its fields as there, the servers' own output going to stderr instead.
  - `.kay/dev/errors.json` lists, as `{ "errors": [...] }`, the errors the servers met, for a reader without a browser such as a coding agent: why the server failed to boot (`kind` `compile`, each problem's `file`, `line`, `column`, `code` and `message` in `problems`, or `boot`), a request that threw (`request`, its `method` and `path`) and an error an island met in the browser (`browser`, its page's path, `island` its component), each with `time`, `message`, `report` (the compile errors as `kay check` prints them, a request's stack on `.kay` lines, or a browser's stack as it sent it) and, where the project's own code threw, `at`: its `file`, `line`, `column` and `frame`, the lines leading to it.
  - `.kay/dev/server-<pid>.json`, `{ "url", "pid" }`, is its address while it runs, which `kay screenshot` reads and `kay dev` removes on exit ([Check, inspect and tool commands](check-and-tools.md)).
  - A boot failure goes once a server boots, a request's error once that method and path are answered without one, and a browser error once its page is served again; requests' errors stay across restarts, the latest 50 kept, and a server not run by `kay dev` writes none, nor does an entry that throws before it calls `pages()`.
  - Under `kay dev`, every element a `.kay` template writes, but the head's, carries `data-kay-src="<file>:<line>:<column>"`, and every page loads the inspector: holding Alt outlines the element under the pointer with that position, from the moment Alt is pressed, Alt+click opens it in the editor, the dev tool's Inspect button does what Alt does until the next click or Escape, for a system taking Alt+click, and its Islands tab, counted on the bar, lists each island's component (a click opens it) with the size of the props the server wrote on it, how long it took to hydrate (the hydration or render itself, not its chunk's download) and the values its signals hold now, numbered in the order its script creates them, refreshed twice a second while the tab shows.
  - The editor is `KAY_EDITOR` (a command, getting the position the way the editor among its words takes it, VS Code, Cursor, Zed, Sublime Text, JetBrains IDEs, code-server, Vim, Neovim and Helix included, as in `tmux new-window nvim`, else the file appended), else `VISUAL` or `EDITOR` when they name one of those that opens a window, else the first of them found on the `PATH`;
  - On a Linux machine with no display, as one reached over SSH, only code-server counts, opening the file in its window already open on the project.
  - With none, the page says so and the terminal prints the position; an editor command exiting with an error within 2 seconds prints its error in the terminal and the page says it failed.
  - A server run any other way, `pages({ dev: true })` included, has the dev tool without the inspector, and a production build has neither.
