# kayjs-auth: The OAuth server for MCP clients and bearer tokens

## OAuth server for MCP clients

- With `pages` and a store keeping `oauth` (`memoryStore` and `pgStore` do), an app is an OAuth 2.1 authorization server with no code of its own: an MCP client (Claude Code, MCP Inspector) pointed at kay's `/mcp` is sent to sign in, the user approves it on a consent page, and it is given kayjs-auth's bearer tokens. `user()`, `via()` (`'bearer'`), `requireUser({ scope })`, gates and `scopes` work on them unchanged. `oauthServer: false` turns it off; `oauthServer: true` throws without `pages` or a store with `oauth`; `oauthServer: { fetch }` replaces the `fetch` used to read client metadata documents (tests).
- Served with no setup: `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration` (RFC 8414; the issuer is the site's origin and `base` from kay.config.ts, else `url`, else the request's origin outside production; in production with neither, its documents and endpoints answer 500 and `/mcp` points at no authorization server, rather than take the issuer from the Host header), the protected resource metadata (RFC 9728) of `/mcp` at `/.well-known/oauth-protected-resource[/mcp]`, which kay serves when `mcp` is on, and the endpoints `<pages prefix>/oauth/authorize` (the consent page), `<prefix>/oauth/token` and `<prefix>/oauth/register`. The 401 of `/mcp` already points a client at the resource metadata. Documents and endpoints answer CORS `*`, and are cached for everyone only when `url` or kay's `site` fixes the origin, else `private`. kay serves the resource metadata unless the app serves that path itself.
- Clients: public only (`token_endpoint_auth_method: none`), by a client ID metadata document (the client ID is an https URL whose JSON names `client_id`, `client_name` and `redirect_uris`; read with no redirect, 5 seconds, 10 KB, never from a private or loopback address, cached 5 minutes) or by dynamic registration (RFC 7591, `POST <prefix>/oauth/register`, ID `kc_...`, 20 per hour per address, and `oauthRegisterAll` caps all addresses together when the app sets it; a client nobody approved is dropped after a day). A client's redirect URIs are 1 to 10, 2048 characters in all, each `https`, or `http` on `localhost`, `127.0.0.1` or `[::1]`, whose port is ignored when matched, as a native app picks a free one; it must equal one registered, never a prefix. An unknown client or a URI it did not register is never redirected to: the page says so.
- Authorization: `response_type=code`, PKCE `S256` required (`plain` refused), `scope` from the app's `scopes` (none asked gives the `oauthServer: { defaultScopes }` the app names, else no scope at all, so the token passes only routes with `scope: false`; an app declaring none gives tokens every scope), `resource` (RFC 8707) must be of this site and given once (several are `invalid_target`, at the token endpoint too), `state` returned with `iss` (RFC 9207). A visitor who is signed out goes to the sign-in page and back; `prompt=none` answers the client `login_required` or `consent_required` instead. Approval is remembered per user and client: signing in again skips the consent page until the user revokes the client, asks for more scopes than were approved, or the request carries `prompt=consent`. Only a user's own session approves: a bearer token or an admin acting as the user cannot. The consent page names the client, the host of its ID and always the host the browser goes back to, lists the scopes, and is never framed. Names lose bidirectional control characters. A route of the app at one of the well-known paths replaces the server's own.
- Tokens: a code is single use and lives 60 seconds; the access token is a bearer token of the approved scopes lasting an hour; the refresh token rotates at each use, is refused after 30 days unused, and its family ends 90 days after its first token whatever its rotations. A code or a refresh token presented twice ends everything issued under it (its family). A refresh cannot add scopes, and one refused for its scope or resource leaves its token unspent (when the store has `oauth.refresh.get`, as the built-in ones do), while a spent one still ends the family; a code exchange refused for its resource or `redirect_uri` likewise leaves the code unspent (`oauth.codes.get`), while a wrong `code_verifier` (the sign of a stolen code), a spent code or one another client presented spends it as before, and a refresh token past its 30 days or its family is invalid_grant and spent, whatever it names. The `resource` asked at authorize stays with the code and is kept by the bearer token and the refresh token, through each rotation: the token request and a refresh may name it again or leave it out, any other (a resource where none was asked included) is `invalid_target`, and the stores read it back as `resource` (`oauth.resource` on a bearer token), null for rows stored before it. Revoking a client, `signOutEverywhere`, banning or deleting the user end the tokens and refresh tokens. The tokens are not in `tokens()`; the account page lists the client instead.
- The consent page, the token form and the lists of tokens and approved apps show each scope as the app words it under `auth.scopes.<scope>` in its messages (`auth: { scopes: { 'posts:read': 'Read your posts' } }`), the scope's code when no catalog has it; a label is shown as text, never as markup, and a language needs its own, as any text the app words. `scopeLabel` is not exported: an app's own page uses `wording('auth.scopes.posts:read', 'posts:read')` from `kay/words`.
- `oauthClients()` lists `{ id, name, scopes, createdAt, lastUsedAt }` of the apps the user approved, and `revokeOAuthClient(id)` revokes one with its tokens (false when none; session only), for a page of the app's own. `oauthAuthorize(params)` and `oauthDecide(fields, allow)` are what the consent page calls.
- Limits (`limits`): `oauthRegister` 20 per hour, `oauthRegisterAll` unset (a ceiling on all addresses together), `oauthDocument` 30 per 15 minutes (metadata documents read for an address), `oauthToken` 300 per 15 minutes.

## Bearer tokens

- `createToken(proof, label, { scopes?, expiresIn? })` answers `{ ok: true, token, id }`: the token, shown this once, for a device or an API client to send as `Authorization: Bearer <token>`. It is minted from a session only, never with another token. `'label'` for an empty label or one over 64 characters (control and direction characters are removed from it first), `'scope'` for an empty list or a scope the app did not declare, `'expiry'` for an `expiresIn` (seconds or a string such as `'30d'`) that is not a positive duration. The token starts with `kat_`, so a secret scanner can match it. It expires after 90 days unless `expiresIn` says otherwise, and `expiresIn: null` is the only way to never expire.
- `scopes: ['posts:read', 'posts:write']` in `createAuth` declares what a token may be limited to, typed from then on. A token given `scopes` passes a gated route only when the route names one of them, `.get('/posts', handler, { scope: ['posts:read', 'posts:write'] })`, any one passing; a route naming none refuses it with a 403, so a route that forgets `scope:` stays closed to limited tokens, and `scope: false` lets every token through. `auth.gate({ scope })` sets the scope of its routes naming none, and `auth.guard({ scope })` does the same for pages. A token made without `scopes`, and a session, pass every scope: leaving `scopes` out is full access, so a token for a script or a device names the scopes it needs. `auth.scopes()` answers the request's token's scopes, null for a session or a token with every scope, and `auth.hasScope(scope)` checks one, for an app's own checks.
- An expired token reads as no token at all, in `user()`, gates and `userFromToken`, and so does a banned user's.
- `auth.issueToken(userId, label, { scopes, expiresIn, token })` mints a token on the server, with no proof and no mail or event: for a flow the app gates itself, such as pairing a device whose owner signed in by provider longer than ten minutes ago, or a script. `token` adopts one the app handed out before, 32 to 4096 characters without whitespace and at least 10 distinct ones, such as a device's JWT, so its devices keep working once kayjs-auth reads them; it expires after 90 days like any other, so pass `expiresIn: null` to keep a legacy device working for good. It answers `{ ok: true, token, id }`, or `not-found`, `banned`, `token` and what `createToken` refuses.
- `tokens()`, `revokeToken(id)` and `enableTwoFactor(code)` need a session too: through a bearer token they answer `[]`, `false` and `signed-out`, so a leaked token cannot list or revoke its siblings nor turn on a second factor. So does everything asking for a `proof` or `reprove()`: the second factor and recovery codes, passkeys, password, address and account deletion answer `signed-out` under a token, whatever proof it sends.
- `tokens()` lists `{ id, label, scopes, createdAt, lastUsedAt, expiresAt, expired }`, since only the token's digest is stored; `revokeToken(id)` revokes one. A use is recorded at most every five minutes. A token ends with a password change, a reset and `signOutEverywhere`, each of which may answer a stolen device, so the devices sign in again after one.
- A token reads as its user in `user()`, guards and gates. A websocket checks the token its first message carries with `auth.userFromToken(token)`, which `createWsAuthStore(verify)` keeps per connection, `await store.get(ws)` checking the token again past 30 seconds and closing the socket once it is refused: the handshake for a client that cannot send a cookie or a header with its upgrade, such as a device's browser widget on another origin.

## Guarding other sites for a reverse proxy

- `forwardAuth: 'example.com'` in `createAuth` (a domain, a list, or `{ domains, requireTwoFactor? }`) serves `GET ${prefix}/forward` for nginx `auth_request`, Traefik `forwardAuth` and Caddy `forward_auth`, and `${prefix}/forward/return`. Domains are checked at startup (two labels at least, no scheme, port or path; kay has no public suffix list, so `co.uk` or `github.io` pass and would open every site under them: name your own domain), and so is a missing `site` or `url` in production. The sign-in session cookie must reach the guarded sites: `session({ cookie: 'login', domain: 'example.com' })`, as a `__Host-` cookie carries no domain.
- `/auth/forward` answers 204 for a person's session with `Remote-User` (username, else email, else id), `Remote-Name` (the same), `Remote-Email` and `Remote-Groups` (roles, comma-joined), always all four, empty when unknown; non-ASCII values are percent-encoded. Otherwise it answers 401 with `Location`: the sign-in page's full URL (`site` in kay.config.ts or `url`), returning through `/auth/forward/return?to=` to the URL asked for when that is `https` on the domains or their subdomains, else the plain sign-in page. `?redirect=1` answers 302 instead of 401, for Traefik and Caddy, which hand the answer to the browser. Every answer is `no-store`.
- It reads the URL asked for from `X-Original-URL` (nginx sets it) or `X-Forwarded-Proto`, `-Host` and `-Uri`. A guest, a bearer token and a session stopped at the second factor are anonymous. `?role=admin` (repeatable, any of) answers 403 for a user without it, inheritance honoured; `requireTwoFactor` sends a user without two-factor (a passkey is not enough: the session does not record how it signed in) to the pages' `account/security` with a 401 (a 403 without the prebuilt pages). The request's own `Remote-*` headers are never read: the proxy must overwrite them on the way to the site. The `proxy_pass` path carries the app's `base` (`/app/auth/forward`), and the shared-domain session cookie reaches the guarded sites too, so strip it there (`proxy_set_header Cookie ""`) unless they need it.
- Only GET: nginx needs `proxy_method GET`. The return route sends anything but the allowed domains (another scheme, credentials, a lookalike host, a relative URL) home.

```nginx
location = /_auth {
  internal;
  proxy_pass http://127.0.0.1:3000/auth/forward;
  proxy_method GET;
  proxy_pass_request_body off;
  proxy_set_header Content-Length "";
  proxy_set_header X-Original-URL $scheme://$http_host$request_uri;
  proxy_set_header X-Forwarded-For $remote_addr;
}
location / {
  auth_request /_auth;
  auth_request_set $remote_user $upstream_http_remote_user;
  auth_request_set $remote_name $upstream_http_remote_name;
  auth_request_set $remote_email $upstream_http_remote_email;
  auth_request_set $remote_groups $upstream_http_remote_groups;
  auth_request_set $signin $upstream_http_location;
  error_page 401 = @signin;
  proxy_set_header Remote-User $remote_user;
  proxy_set_header Remote-Name $remote_name;
  proxy_set_header Remote-Email $remote_email;
  proxy_set_header Remote-Groups $remote_groups;
  proxy_pass http://127.0.0.1:8080;
}
location @signin { return 302 $signin; }
```

- Traefik: `forwardAuth: { address: 'http://auth:3000/auth/forward?redirect=1', authResponseHeaders: [Remote-User, Remote-Name, Remote-Email, Remote-Groups] }`. Caddy: `forward_auth auth:3000 { uri /auth/forward?redirect=1; copy_headers Remote-User Remote-Name Remote-Email Remote-Groups }`. Behind a proxy set `proxy: { hops: 1 }` in kay.config.ts so limits count the visitor's address.
