# kayjs-ui: Infinite lists, LoadMore and a Table over them

## Common tasks

### infiniteList, LoadMore, Table(list)

- `LoadMore(list={people})` after a list (`button` swaps the sentinel for a "Load more" button; a status tells screen readers how many rows a page added), with `const people = infiniteList(firstRows, { limit: 20, key: row => row.id, load: ({ offset, last }) => fetchPage(offset) })` from the package, draw `people.rows()`:
  - `limit` is a full page: a shorter one ends the list. `load` resolves to the next page, `offset` counting every row fetched and `last` the last row fetched for a cursor source. One page loads at a time.
  - `Table(list={people} columns={...} rowKey=...)` draws `people.rows()` with `LoadMore` after them, and its header clicks sort on the server: `people.sortBy(sort)` starts the list over from offset 0 and `load` gets the sort as `sort` beside `offset` and `last` (`infiniteList`'s `sort` option is the order the first page is in). A column is sortable by carrying a `sortValue` (`numeric` ones have it), which only marks it here. The table's `sort` and the URL's `sortParam` sort reach the list too, and a sort restarts it, so a selected row outside the first page leaves the selection. The list also loads again on mount when the table's sort differs from the `sort` its `infiniteList` was made with, and a boolean `exportable` exports the loaded rows only.
  - A Table over the list filters on the server too: its search box (`filter`, or just `filterParam`, shows it) hands the typed text to `load` as `filter.text`, after a pause in typing and from offset 0 as for a sort, and the loaded rows are not matched again. `fields={[{ key: 'origin', label: 'Origin', options: [{ value: 'a', label: 'A' }] }, { key: 'tag', label: 'Tag' }]}` adds a select (with `options`) or a text box each, their values reaching `load` as `filter.fields.origin` (only the non-empty ones) and the page's URL under `key`, which may not be a name the table writes itself (`sort`, `direction`, the search's `filterParam` or `q`, `sortParam` and its direction): such a field throws as the table is made. `filterParam` keeps the text there. The list begins as `filter: { text, fields }` says (`infiniteList`'s `filter` option) and loads again on mount when the URL's filter differs; a sort and a filter changed together load once, and a sort clicked while the text waits for its pause loads at once with it. `people.filterBy({ text, fields })` and `people.restart({ sort, filter })` do the same from code; a field left out is empty. `exportable` as an address also gets the fields, under their `key`. With an action source, a function `input` reads `at.filter`.
  - A list follows what it reads, which a `persist` island's new props change: an action source's function `input` that reads a signal or a prop (called once with `offset: 0` and no `last` to find what it reads, in any island) starts the list over from the first page that input asks for, and first rows given as a function, `infiniteList(() => rows, ...)` with `rows` a prop, start it over from the new rows. A list made from a plain `rows` array and an `input` reading no prop keeps its rows; give the island another `persist` value per input instead.
  - `key` drops a row a later page repeats; leave it out when the source cannot repeat one.
  - A `load` that throws or resolves `undefined` (an `attempt` that toasted) stops the list on an alert with a retry button, loading no other page until it is pressed.
  - An action as the source, in place of `load`: `infiniteList(first, { limit: 20, key: row => row.id, action: listPeople, input: { team }, failure: 'Could not load people.' })`. Each page calls it with `{ refresh: false }` through `attempt`, so a failure toasts `failure` (a string or `attempt`'s options) and fails the page, and `input` is the call's other fields, `offset` and `limit` (the page size) being added. A function `input: at => ({ q: at.filter.text, before: at.last?.id })` answers the call from `PageAt`, for a cursor, a sort or a filter, with `offset` and `limit` added under what it names itself, and `undefined` loads an empty page. `rows: answer => answer.items` reads the rows out of an answer that is no array, and is required then.
  - `pageFields(max = 500)` from the package is the pair `offset` and `limit` for the action's schema, `s.Object({ ...pageFields(), team: s.Optional(s.String()) })`, with the bounds named once. `pageOf(rows, input)` cuts a list the server holds whole to `limit` rows (100) from `offset`, answering `{ rows, total }`: the action and the page rendering the first rows both call it, so neither slices by hand.
  - `people.patch(id, change)` updates the loaded row `key` reads as `id` (so the `key` option is needed) from the fields to merge or a function of the row returning it, and answers whether a row matched: a toggle's action answering the row as the server holds it reads `people.patch(row.id, await flag(row.id, { refresh: false }))`. An `undefined` change, such as a failed `attempt`'s, changes nothing; the other rows keep their identity, a merged row its prototype, and a function changing the row's key lets a later page bring the old key as a row of its own.
  - `people.reload()` loads again every row loaded so far (page after page, from offset 0, with the sort and filter in force) and swaps them in at once when they land, for a page refreshed after the data changed: a page on its way is dropped, and a `for row of people.rows() key={row.key}` keeps the DOM of the rows whose key is unchanged, so the scroll holds. `people.reload(rows)` takes the first rows from the page instead of loading them. A failed reload keeps the rows shown and fails nothing, a list that had ended loads on until a short page, and nothing happens while `sortBy`, `filterBy` or `restart` loads its first page.
  - It draws the WhenVisible sentinel, a `status` row while a page loads and the alert. `loadingLabel` (`Loading more…`), `failureLabel` (`Could not load more.`), `retryLabel` (`Try again`) and `margin` are its props; `people.ended()`, `status()`, `pending()` and `error()` read the state.
  - An `infiniteList` is a Source, as a `resource` or a `stream` is: `status()` is `loading`, `failed` or `ready`, `error()` the failure of the last page as an `ApiError` (what `load` threw, else status 0 with `failure`'s words), kept until a page lands, and `retry()` loads that page again. `failed()` stays as `error() !== undefined`. `LoadMore(list={...})` takes any object with `rows`, `ended` and `more` that is a Source too (`LoadMoreSource`), and `Notice(source={people})` shows the error with a retry anywhere on the page.

## Reference

- Every `infiniteList` option and method is typed in the package (`InfiniteListOptions`, `InfiniteList`), with its behaviour in the notes above.

### Table and VirtualList sources, busy and row links

- `rows` (Table) and `items` (VirtualList) take an array, a function returning one, or a promise of one, as Menu's `items` does. An array is drawn by the server. A function is called in the browser only, so it may touch `window` and the server never runs it, and a promise's answer lands in the browser; the server draws `skeletonRows` / `skeletonItems` (5) skeletons for both. A refresh (a new function or promise, a retry) keeps the rows shown, and a rejection keeps them too, beside a `failureLabel` alert with a retry (`retryLabel`) that calls the function again; a bare promise cannot be asked twice, so it gets no retry. Only the latest answer lands, and `onLoad` hears a function's synchronous answer too. `onLoad(rows)` and `onError(error)` mark each transition, and `loadingLabel` (a status screen readers hear), `failureLabel` and `retryLabel` word them (`ui.table.*`, `ui.virtualList.*`).
- `busy` draws the skeleton for a source the app loads itself: over no rows the skeleton replaces `@empty`, over rows they stay dimmed with `aria-busy`. A `list` still on its first page with no rows (a sort or filter restart) is busy too; a failed page keeps `LoadMore`'s alert and retry. The skeleton parts are `skeletonRow`, `skeletonCell` and `skeletonBar` (Table), `skeleton` and `skeletonBar` (VirtualList), the failure `failure`, the screen reader text `status`.
- `rowHref(row)` makes each row a link (undefined for a row that leads nowhere) and `onRowClick(row, event)` a button, or hears the click of a link row (`event.preventDefault()` to navigate yourself). A `tr` cannot be an anchor, so the first cell holds a `rowLink` anchor or `rowButton` stretched over the row, named `Open <first column's text>` (`openRowLabel(row)`): middle click and open in a new tab work, and the checkbox, the toggle and the links and buttons the cells draw stay clickable above it. The link covers the row, so the mouse cannot select its text and a `tooltip` on the row's own content does not show; put them on a control, which sits above. VirtualList has `itemHref(item, index)`, `onItemClick(item, index, event)` and `itemLabel(item, index)` (`itemLink`, `itemButton` parts) the same way.
- `Table(columns={columns} rows={() => fetchPeople()} rowKey="id" rowHref={person => person.url})`.
