# The editor on the page

Content edited where it renders: in edit mode kay marks each element showing an entry's field, and the editor panel changes them with a live preview, with nothing for the app to write.

## Common tasks

### Enter edit mode

Edit mode is kay's preview mode, so the app sets `preview: {}` (its cookie is signed with a key derived from `KAY_SECRET`); a signed-in editor opens a page in it from `<prefix>/page?path=` or the Edit this page link, and leaves it with Stop editing. A link from another site (`Sec-Fetch-Site` neither `same-origin` nor `none`, or `Sec-Fetch-Dest` not `document`; a browser sending neither enters at once) lands on a button that posts to enter, so a browser that sends those headers cannot be put in edit mode by another site. The editor names the other editors of the entry to a person the app's guard let in, and only counts them for the holder of an edit link, whatever component renders it: the server strips the names of the entry's rooms from the members sent to a request in edit mode that no guard admitted. The guard marks the edit cookie it lets in with a signed cookie of its own, so the mark holds across restarts and replicas; a person who entered by an edit link is marked at their next screen, write or read of an entry, and an open stream follows at its next recheck on the server that marked it, and any other at its next connection. A guard that turns an edit link's holder away is asked again at each of their reads. An edit cookie issued before this release is not marked: entering edit mode again from the Edit this page link issues a new one.

```ts
export default defineConfig({ preview: { secret: env.PREVIEW_SECRET }, extensions: [cms({ guard, files })] })
```

### Make a field editable on the page

Render the entry's field as usual: kay marks the element itself in edit mode, so a click opens the field in the editor, or types in it where it stands: a text, a long text and a paragraph, heading or list item of Markdown ([Typing on the page](screens.md)). An image field rendered in an attribute (`<img src>`) gets a Replace button over it under the pointer or the focus, and takes a file dropped on it (`page-images.ts`, `page-image-tools.kay`): the file goes through `uploadFile`, the draft takes its path and, when the field keeps them, its size (`image-value.ts`), and a refusal is toasted. A file the field does not accept (its `accept`, else the server's image types) is refused before the upload with the form's `cms.file.rejected` wording; a file dropped on an image of an entry still a row is kept from the browser, opens the entry and replaces the image once it has loaded; while an image of a list item uploads, the page's list bars change nothing in that entry (`holdEntry`), so it lands in its item.

```kay
h1 {post.data.title}
img(src={post.data.photo} alt={post.data.title})
```

### Keep a fixed header clear of the panel

The panel pads the page's `body` by its width or height, and `html.kcms-editing` carries `--kcms-width` and `--kcms-height` for a site that wants to line up with the panel.

```css
html.kcms-editing .toolbar { right: var(--kcms-width, 0px) }
```

### Keep unsaved edits across a reload

The on-page editor keeps its drafts in `localStorage` with `browserKeeper()`; a site building its own editor passes it to `createDrafts`.

```ts
const drafts = createDrafts({ show, delay: '150ms', keep: browserKeeper() })
```

## Reference

- The app writes no marker: in edit mode kay marks each element rendering an entry's field itself, `data-kay-field="<collection>:<slug>[@<locale>]:<path>"`, each segment URI-encoded, the path dotted with list indexes (`sections.1.heading`). A field in an attribute is `data-kay-field-<attribute>`, a field sharing its element's text sits between `<!--kay-field …-->` and `<!--/kay-field-->`, fields are marked wherever the data is read, a component handed the entry's data included, and a Markdown body is `data-kay-body="<collection>:<slug>"` or a `kay-body` comment pair.
- The body's path is the `BODY` symbol, never a string, so a data field named `body` stays a data field.
- Outside edit mode the page is unchanged and the editor is not rendered.
- Each entry of the panel has Publish or Unpublish (a confirmation; collections with a draft flag) and Delete (not a single collection) in a row under its head, disabled with the role's reason when `roles` refuse them; Publish and Unpublish save the draft flag alone and refuse with edits not saved, Delete names the entry's referrers and locks the form; it reads the page again, or, when the page shown is the deleted entry's own, goes to the collection's screen (`<prefix>/collections/<collection>`) instead of a 404, replacing it in the history; when leaving is declined over edits of another entry, the form is replaced by a notice linking that screen. A save started while the Delete confirmation is open leaves it open, its confirm button disabled until the save ends.
- An entry's head names the entry (its title in the list), with its collection and locale under it; a single collection shows its title alone. A click on a field of the page, or typing in one in place, collapses that entry's form to the item holding it (`EntryFields` takes `only`, an item's name, `#body` for the body; the other items stay rendered and hidden, so what was typed in them is kept and Save writes the whole draft). A click on a field puts the caret of its input where the click landed (`caret.ts`: the text around the click is looked for in the field's value, a Markdown one without its markup, and the occurrence nearest the click wins; a text it finds nowhere keeps the focus as before). An anchor per item, in the layout's order, shows another and focuses it; Show all fields opens the form; focusing a field of the whole form collapses nothing; a save refused on a hidden field opens the form. With several entries on the page, each starts as a row with an Edit button (`entry-slot.kay`) and its form, GET and inline source load only once it is opened by that button, a click or typing on one of its fields, or edits kept for it in the browser, so layout entries nobody edits cost no read; a page with one entry opens it at once, an opened entry stays open until Stop editing, and Save all (`save-all.ts`) saves each one holding edits in the page's order, one after another, and an entry the server refuses stays unsaved with its message while the others still go through.
- Above an entry's form the editor names the fields of it the page cannot let a click reach (`EditorProps.unclickable`): a transformed value, an island's props, a frozen object.
- The editor panel never covers what it edits. It is kayjs-ui's docked `SidePanel` (`dock`), and the marker choice among a field's elements is its `Menu` opened `at` the click: from 64rem the panel docks to the right and pads the page's `body` by its width, below that (and always below 40rem) it is a bottom sheet padding the `body` by its height, so the page keeps its width and a fixed header at the top stays in view (at the side the panel starts under a header fixed or sticky across the top, at most 240px tall and touching it, found by itself and given to the panel as `--kui-dock-top`; one added later is found on the next scroll or resize). A visitor drags or arrow-keys its inner edge (a focusable `separator`) to resize it, switches the dock with the head's button (from 40rem), and hides it to the `SidePanel`'s `launcher` button; the dock, sizes and hidden state are kept in `localStorage` (`kcms-editor`). The dev tool docked at the right or bottom publishes `--kay-dev-inset-right` and `-bottom` on `html`, and the panel sits beside it, clamped so the page keeps 22rem (10rem tall); the open panel publishes what it holds as `--kay-panel-right` or `-bottom` on `html`, which the dev tool's bar and floating drawer keep out of (the collapsed button publishes itself the same way; the bar publishes its measured room at a bottom corner as `--kay-dev-bar-bottom-left` or `-right`). Escape does not hide the panel, only its close control does. A click on a marked element scrolls it above the bottom sheet, and an entry's head is a `PageSection` with `sticky` and a `subtitle`, so it stays on one line. The buttons over a page list item are a floating kayjs-ui `Toolbar`, and Stop editing over unsaved edits asks in a `Dialog` (Keep editing, or Drop them and stop). `html.kcms-editing` carries `--kcms-width` and `--kcms-height`, the panel's size at the edge it is docked to (0 at the other), for a site that wants to line up with the panel.
- Unsaved edits of the on-page editor are kept in `localStorage` (`kcms:draft:<person>:<entry>` for the editor's own `browserKeeper(get, now, who)`, `kcms:draft:<entry>` for `browserKeeper()`, a week at most; kept under who the admin let in, so another person on the browser finds none, and all forgotten at Sign out), cleared on save, Reset and Stop editing, and brought back after a reload, a crash or in a second tab with a note; a draft made from an older version of the entry (or, for an entry with no version, from another saved copy) is dropped with a note, never offered, and the write waits for the pause before the page renders again. A reload or a link with edits unsaved on the entries the page shows asks first (`guardLeave`), and Stop editing asks too: Keep editing or Drop them and stop. A conflict lists the fields both sides changed and offers Keep my edits or Take their version (`drafts.adopt`).
- Draft rendering happens on the server: the editor sends the changed entries, kay renders the page with them and swaps it in, islands kept. An entry the schema refuses shows its saved text while the others keep their preview, and the editor names it; a status line (`role="status"`) says `Updating the page…` while it renders, the drafts render again after in-app navigation, and for five minutes after a forge save (kept in `localStorage`) it says the live site may still show the old content, also after leaving edit mode and coming back.
- Every change goes through one API, `POST` and `DELETE /_kay/cms/entries/:collection/:slug` (and `GET`, which answers `{ collection, entry }` as the editor opens the entry, `?locale=` for a localized one, a 404 for a missing entry), `POST …/:slug/publish`, `POST …/:slug/duplicate` (a draft copy, answering its `slug`), `GET /_kay/cms/entries/:collection` (the entries a reference can pick, `[{ slug, title }]`) `POST …/:slug/move?direction=up|down` and `POST /_kay/cms/markdown` (`{ markdown }`, answering the sanitized `{ html }` of the editor's Preview, 422 for a text kay cannot read), from the sidebar and from the screens alike. kay validates the data against the schema and names the file; kay writes nothing, the configured `files` saver does.
- The app imports kayjs-ui's theme. The screens and the editor render their own `Toaster` and `TooltipHost`, which render nothing while the app's are mounted; kayjs-ui is a peer dependency, so both resolve the one copy that guard lives in.
- Edit mode is kay's preview mode, so the app sets `preview: {}`, its cookie signed with a key derived from `KAY_SECRET` unless `preview.secret` gives one. An edit cookie or link reads through the API only the entries the pages it rendered in edit mode read (the editor's own entries; a signed-in editor the guard admits reads any), and leaves edit mode. It saves, publishes, deletes and uploads only under `kay dev` without a `guard`: with a `guard` every write needs it, and any other server without one (`NODE_ENV` unset included) refuses every write from an edit cookie or link and warns at boot, naming `cms({ guard })`, since the cookie is tied to no user. The scope is kept in memory per server, so after a restart, or on another replica, the page is loaded again before its editor reads; `editedEntry(request, collection, slug)` from `kay/server` is what the API reads it from.

### Dev tool

- `cms()` adds a CMS tab to the dev tool under `kay dev`, with nothing to add in the app: whether the visitor is in edit mode, a button into it for the page shown (through the screens' `page` route, so the guard decides) and one out of it (the `preview/exit` route). It reads `/_kay/cms`, a route mounted under `kay dev` alone.
