# kay

A Bun web framework: `.kay` components (pug-like templates over TypeScript), compiled to HTML on the server and to kay's own DOM runtime in islands. `llms.txt` and `llms/` are what an app's author reads; `src/` is the framework, `docs/` the documentation site built with kay itself (a workspace, so it imports kayjs-ui from `packages/`), `packages/` kay's libraries (kayjs-auth, kayjs-ui, kayjs-mail, kayjs-cms, kayjs-ai) as Bun workspaces, each with its own tests, `llms.txt` and eslint config. An issue about a library carries its label (`auth`, `ui`, `mail`, `cms`, `ai`); kay's own issues carry none. Every issue also carries one priority: `priority/high` (breaks apps or CI, or blocks a migration), `priority/medium` (a real cost to apps or sessions) or `priority/low` (exploration, polish), one kind: `kind/bug`, `kind/feature` or `kind/chore` (tests, tooling, benches, docs, refactors: nothing an app sees), and one size: `size/small` (one lane), `size/medium` (a few lanes or a day) or `size/large` (a design pass first, likely split); a new issue gets all three when filed. An issue blocked on a Bun fix also carries `waiting/bun`, naming the Bun issue or PR and the kay workaround it lets go.

## Design rule

Every feature asks the least of the app: the fewest declarations, the easiest setup, no workaround on the app's side. Prefer a design harder to build inside kay over one the app has to wire around.

A kay component or library API is customizable from its first version, so an app does whatever it wants without wrapping it, copying it or waiting for an issue. Before a component is done, each of these has an answer: its data comes from a list or from an async source (a function returning a promise), each visible part can be replaced or extended (a block, a part, a class), anything that navigates can be a link as well as a button, its state can be controlled by the app or left to the component, and a callback or event marks each transition (open, close, select, load, fail). A gap an app finds later is a miss against this rule: filed with the component's label, and fixed for every component of its kind, not only the one the app used.

## Workflow

Each session works alone, with no coordinator:

1. Take an open issue, the highest priority first: `ft board -L priority/high` lists open issues as available, taken by a session running here, or claimed by one no session here answers to. `ft take <n>` claims it with a `Taken by session <name>.` comment and refuses one a live session holds; `--take-stale` takes over a claim whose session is gone. `ft issue <n> -c` reads it: the description, its boxes numbered as `ft tick` takes them, and the comments. `ft` (@kaynooo/forgejo-tools, installed with `bun -g`) runs over `tea`, from the repo.
2. Work in a worktree (`just worktree <name>`), and commit with `bun run lint:fix` and the tests of what changed. A change heading for a `high` review first lists the cases a reviewer would try in the issue's **Cases** (each `base`, `trailingSlash`, locale, dev or production, island or server path, hostile input that reaches the code) and writes them as tests before the fix.
3. Review the commit once, through the `requesting-code-review` skill, at an effort matching the diff: none for docs, tests or a few lines, `high` only for the runtime, the compiler or the build, `low` for everything else. Its fixes go in a follow-up commit, not reviewed again unless they reshape the change; then a second, last review at `low` covers that follow-up alone, and the same lane fixes what it finds in one more commit, not reviewed again, rather than filing it as a new issue.
4. `just land` (`scripts/land.ts`): landings verify side by side, it rebases on origin's main, lints, checks, runs the tests the changes reach (`bun test --changed` plus the tests reading `llms/`, `docs/`, `examples/`, `packages/` or a fixture as files, the full suite for a root config unless only dependency versions changed, which leaves it to CI, then the suite of each library the change touches and of each depending on one whose `src/` changed, as kayjs-ui reaches cms and ai), pushes main and moves the main checkout to it. It prints one line per step, keeps their output in `land.log` in the worktree's git folder, and a failure ends on the step's failed tests and last lines, exiting 2 (uncommitted changes, nothing to land, a merge marker line added), 3 (conflict with main), 4 (a step failed) or 5 (push refused). Only the push is one landing at a time: it takes a lock once verified and pushes at once when origin's main has not moved since its rebase, else rebases and verifies again under the lock, so run it in the background. A scope with a memory limit under 16 GB sizes the test runs itself (`scope-memory.ts`): 3 workers and 4 shards in 8 GB, which held 5.5 to 6.7 GB at most, 1.2 to 2.6 GB of it the session's other work, and `KAY_LAND_WORKERS` and `KAY_LAND_SHARDS` override it. The step's `peak` and `memory.peak` count the page cache the kernel gives back before it kills, so the `held` figure (anon, tmpfs and kernel memory) is the one that has to fit; set `KAY_LAND_WORKERS=2` when other lanes run big test runs in the same scope (each step also waits for a `slot` and runs under `nice -n 10` where they are installed, and the test runs hold one named lock, so one runs at a time machine-wide and landings queue across sessions while the host's other work keeps the CPU; `KAY_LAND_SLOT=0` and `KAY_LAND_NICE=0` leave them out; a host keeps these, and the test database URLs, as `KEY=value` lines in `.git/kay-land.env`, which every worktree reads and a variable already set overrides, so a session runs `just land` bare), and `KAY_LAND_SHARDS=4` when the tests outgrow that memory, which runs the whole suite or the tests the changes reach as 4 runs one after another (a worker keeps the global of each file that loaded a native addon, oven-sh/bun#46561). Never run the full suite locally: CI runs it on every push, and a red run on main is fixed by whoever landed it; `just ci <sha>` (`ft ci`) waits for the run covering a landed commit and prints its failed tests.
5. Tick its boxes as they land (`ft issue <n>` numbers them, `ft tick <n> <box>...`), close it with `ft fixed <n> <sha>`, which comments `Fixed in <sha>` and refuses while boxes are left, remove the worktree, and tell the user the one line it landed as. An unlanded branch left behind is a comment on its issue, naming the branch and where it stands.

A session handing issues to subagents lands for them: a subagent goes through steps 1 to 3 in its worktree, claimed by the session with `ft take <n>... --lane` (`lane-<s>-<n>`, `<s>` ending the session's name, live while the session runs), and returns at "ready to land", naming its worktree, its issue and whether steps remain. The session runs `just land` from that worktree in the background, then sends a failure's output back to the subagent to fix, does step 5 itself for a finished issue, or tells the subagent the sha it landed as to go on with the rest. A subagent leaves its worktree alone while it lands, as the landing rebases it.

## Checks

- `bun run check` is kay check (types, templates included), then kay's `src` again under `tsconfig.consumer.json`, the compiler options of an app without `exactOptionalPropertyTypes`, which an app's `kay check` reads kay with. `bun run bench:check` checks every benchmark app, `bench:check:kay` the one on kay alone. A change under `packages/<name>` runs `bun run check` and `bun run test` in that folder too; the root lint already covers it, linting kay then running each library's own lint in turn, one process each. The root lint is `scripts/lint.ts`: one process per group of type-aware files (`eslint.slices.ts`) under a 2 GB heap, as an uncached group outgrows 1.5 GB, about 80 s, and `just land` runs it; while working a lane lints the files it changed (`bunx keslint --cache <files>`), never the whole root.
- `bun test tests/<file>.test.ts` while working, and several files as `bun test --parallel <files>`: a plain `bun test` runs them in one process, which serves one project, so files on different fixtures fail there by design; the whole suite as `bun run test`, every file at once in this checkout (`bun test --parallel`, the slowest first by `.kay/timings.json`, which `scripts/timings.ts` builds before each run from `tests/timings.json` (the fallback) and the last green CI run's measurement, a file with none starting early), as CI runs it on half the cores. A test that writes into a fixture works on `fixtureCopy()` from `tests/scratch.ts`, and its scratch files go under `scratchDir()`, so no other file's build meets them.
- The size ratchet: `src/` of kay and of each library may hold a file of 600 code lines, a function of 150 lines and a complexity of 40 at most (`eslint.ratchet.ts`), and a file past one of them is listed in `eslint-ratchet.json` with the value it has. Its lint fails past that value, so a file in the baseline cannot grow; `bun scripts/ratchet.ts`, which `scripts/lint.ts` runs last (so `just land` does), fails when a recorded value is above what the file measures now, and a lane that split or simplified a file records the smaller value with `bun scripts/ratchet.ts --update` and commits `eslint-ratchet.json`. The update refuses to raise a value or to add a file already committed; a file split out of another is new, and enters at its value. `--distribution` prints how the files spread over each limit.
- The eager JS of five pages (the static fixture's home, i18n-links, live-values, the bench app's products and table) is held by `bench/sizes.json`: `just land` runs `bun scripts/sizes.ts` on every landing and stops when a page grew more than 100 B past the baseline, and a lane whose JS growth is intended accepts it with `bun scripts/sizes.ts --update` and commits `bench/sizes.json` with the change. A shrink is recorded with the same command, and CI only prints the table.
- `tests/memory.json` keeps the peak memory in MB of the process and its children for the heaviest test files, as `tests/timings.json` keeps their times: `bun scripts/test-memory.ts --update <files>` measures each file alone and prints the ones past 500 MB and those that grew past what is kept; a landing's log ends each step on the scope's `memory.peak`, and a killed worker is named with its file.
- The slow files: `new.test.ts` (scaffolds and type-checks apps), `browser.test.ts` (Chromium through `BUN_CHROME_PATH`), `docs-contrast.test.ts` (builds the docs, axe-core in Chromium), `check.test.ts`, `forms.test.ts`.
- `examples.test.ts` and the app template's own tests run only with `TEST_DATABASE_URL`, a Postgres whose user may create databases.
- Test runs in one checkout wait for each other (`tests/one-run.ts`), as they build into the same `.kay` and fixtures; the workers of one parallel run share its turn. Work in parallel from a worktree instead: `just worktree <name>`, which Claude Code's own worktrees also go through (`.claude/hooks/worktree.ts`), starts at HEAD with its dependencies installed.

## A change is done when

- `api/` says what the public surface is: `bun scripts/api.ts --update` regenerates the snapshot of every export and its type, kay and each library (`tests/api.test.ts` fails for any difference, in about 8 s). What the docs call internal (`INTERNAL` in `scripts/api.ts`) goes to `api/internal/<package>.txt` and changes with no flag. A removed or narrowed export is refused unless the update is run with `--breaking`, which records every break of the run, or `--break="<key>"` (repeatable, the refusal prints the keys), which records that one alone; either records it in `api/breaking.txt` and obliges its line in `llms/upgrading.md`; a changed export that breaks nothing (an optional member added, a type widened) takes `--compatible` instead, which records nothing but the `--break=` keys of the same run, and a removal still needs `--breaking`; `just patch` refuses while that file lists anything; a minor of a 1.x kay ships it and clears it, as `just major` does, and from 2.0.0 a minor refuses too (#2595 box 5 drops the 1.x allowance).
- `llms/` and `docs/src/content/docs/` say what changed, in the same commit; `tests/llms.test.ts` and `tests/docs.test.ts` compile their `kay` blocks, check every lint is listed and keep `llms.txt` under 10,000 characters.
- A breaking change `kay check` can recognise ships the old form as a lint in the `deprecated` group, with its `since` minor and a safe fix in the same commit, and the commit says in the changelog why it cannot when no such lint is possible. The lint stays three minors, then goes with the old form: the release that drops it removes the lint and its upgrade line, and `tests/upgrade.test.ts` fails for one left past its three minors unless it is listed there as waiting. Declare it in `src/compiler/lints.ts` as a lint with `group: 'deprecated'` and its `since` minor, its check emitting a `safe` fix, and `kay upgrade` and `kay explain deprecated` pick it up.
- Every file under `llms/` and each library's `llms.txt` stays under 25,000 bytes (`tests/llms.test.ts`), so an agent reads it with one command: a topic that outgrows it splits along its headings into a new file that `llms.txt` lists. `just patch` and `just minor` keep `llms/upgrading.md` under 20,000 bytes and `llms/whats-new.md` under 14,000 with its newest release cut to 10,000 (the rest moves to the archive as `## <version> (continued)`, `capNewest`), so lines added under `## Unreleased` always have room, moving oldest releases into `whats-new-archive.md` and `upgrading-archive.md` (`archiveOldest` in `scripts/whats-new.ts`), and an archive over 24,000 bytes drops its oldest releases, which their tags' release notes keep (`trimArchive`).
- A new lint has its row in the table of `llms/lints.md` and in `docs/src/content/docs/reference/checks.md`; `tests/llms.test.ts` and `tests/docs.test.ts` fail for one missing from either.
- A feature an app sees adds its line, linking where it is documented, under `## Unreleased` in `llms/whats-new.md`, opening that section when it is the first; `just patch` and `just minor` name it after the version, and the release notes open with it.
- A breaking change adds what an app changes under the next minor's section of `llms/upgrading.md`, opening that section when it is the first.
- Breaking changes ship as minors; a major is a rewrite.

## Releases

`just patch` or `just minor` moves kay and every library to one version (`scripts/version.ts`: versions, each library's peer on kay's minor, the lockfile; `tests/packages.test.ts` holds them together), tags and pushes both at once, dropping the bump when `tests/upgrade.test.ts` finds a deprecation past its three minors at the new version; before it, `scripts/release-apps.ts` waits for the Apps workflow (`.forgejo/workflows/apps.yml`, dispatch only, never on a push) on the commit being released, dispatching it when no run covers it: it packs kay and each library, clones every app of `scripts/apps-ci.ts` (the `kay-sites` memory's apps with a remote) from Forgejo with the read-only token stored as the Actions secret `KAY_APPS_TOKEN` (scope `read:repository`), points their kay and kayjs-* dependencies at the tarballs and runs each app's own check, lint and test, one step per app; an app's test that needs its own compose stack is listed in `APPS` as skipped, with the reason it prints, `BLOCKING` in `scripts/release-apps.ts` is false until every app is upgraded to the last 1.x minor (#2595), so a red run is printed and the release goes on, and `KAY_SKIP_APPS_CI=1` skips the wait; a new app on kay is added to `APPS` and to the workflow's steps (`tests/apps-ci.test.ts` holds them together). The tag's workflow publishes kay and each library not marked `private` to the Forgejo npm registry. A library's ranges on another are `workspace:~`, which publishing writes as that version.
